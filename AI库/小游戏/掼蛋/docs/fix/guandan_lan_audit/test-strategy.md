**■ 四、测试建议**

**▍ 4.1 扩展方向（建议在详细测试文档中展开）**

1. **测试数据准备**
   - 牌局数据：固定种子的发牌序列（便于复现"重复牌伪造炸弹""AA2233 判型"等用例）；一副已知手牌的玩家状态快照。
   - 身份数据：成对的合法 token / 过期 token / 伪造 token / 空 token；同名不同 token 的两个客户端。
   - 号码数据：自定义号 + 自动号混合序列；0/负数/小数/9999+/非数字 的非法输入集。
   - 注入数据：`<script>`、`<img onerror>`、超长串（1KB/64KB/65KB 边界）、控制字符、emoji + 中文混排昵称。
2. **自动化测试**
   - **可复用骨架**：`_accept.js`（无头 Chrome + CDP 真点击）已覆盖"开房/占号拒绝/僵尸回收/file:// 拦截/自动重连"5 条，建议扩展出 SEC-01～SEC-06 与 IT-02/IT-04。
   - **裸 WS 探针**：`gd_ws_probe.js`（列房间/开房/撞号）可直接做越权与会话类用例的脚本化。
   - **候选自动化清单**：UT-01～UT-10、IT-02/IT-03/IT-04/IT-08、SEC-01～SEC-07、RB-02；**不建议自动化**：真人手感、布局、观战视觉。
3. **性能测试**
   - 指标：单条广播端到端延迟、开房响应时间、8 并发房间下服务端内存与事件循环延迟。
   - 基准：以修复前（v2.1.3）同场景数值为基线；告警阈值建议 +30%。
4. **安全测试**
   - 建议按 OWASP WebSocket 清单补：Origin 校验覆盖（含 `Origin: null` 决策记录）、每动作鉴权覆盖表、限流与 `maxPayload` 生效证明。
5. **可测性改造建议（不改业务语义）**
   - 把"30 秒 AI 接管时限""出牌倒计时（15s/30s）""心跳间隔""重连退避"抽成**可配置常量**（如环境变量或 `config` 对象），否则相关用例每条都要真等 30 秒。
   - 为服务端加**结构化事件日志**（一行一条、含 `roomId/playerId/动作/结果`）到文件或 stdout，便于断言"发生了什么"——当前只有 `console.log`，无法在被测环境外取证。

**▍ 4.2 注意事项**

- **jest 假绿**：`guandan.test.js` 是引擎副本，不 require 服务端 → 修服务端后必须做"副本同源"核对，否则测试通过没有意义。
- **`ai-players-test.js` 会先碎**：它按 `playerId` 直发 `play`，身份绑定改造后必须同步改造该脚本，否则回归会以"脚本失效"的假失败开场。
- **每次改动都清空房间**：任何触发服务器重启的改动都会掉线全部玩家（客户端会自动重连，但房间需重建），测试期间的用例设计要避免把"重启"与"对局中"混为一条用例。
- **两套客户端来源**：客户端由服务器在 `/` 直吐 → 协议类用例务必**先 F5** 确认拿到与被测服务端同版本的页面，否则会测出"新旧协议不匹配"的假问题。
- **旧标签页兼容**：FIX-006 后旧页面（localStorage 无 token）的重连被拒属**预期行为**，测试需区分"预期拒绝"与"回归失败"。
- **环境约束不算失败**：企业 GPO 管控的防火墙下，手机/其他电脑连 `http://<本机IP>:8081` 可能被拦且用户无法自行放行（`LocalFirewallRules N/A`）→ 场景6 应记录为环境限制。
- **只在无人在玩时执行破坏性用例**（半开连接、重启、洪泛），避免影响真实玩家。
