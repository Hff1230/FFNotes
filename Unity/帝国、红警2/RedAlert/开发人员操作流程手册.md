**▍ 0.2 标准操作流程（八步，适用任何模块）**

```text
① 定位模块        → 0.1 表对号；确认不是"跨模块"问题（见 §九）
② 读该模块文档    → 「模块总览 + 流程图」两章必读，尤其"核心文件表"与"数据流"
③ 找落点          → grep -rn --include="*.cs" '关键词' .        ⚠️ 不要用 rg（见 0.3）
④ 判断改动类型    → 配置表 / 服务器数据 / 表现层 / 逻辑层，四类的验证方式完全不同：
                     · 配置类：改完必须"重启或热更后重新加载"才生效（各模块加载时机不同！）
                     · 服务器数据类：客户端改完只能等服务器配合，别自己造数据
                     · 表现层：编辑器内看得到，但要按"游戏机位"验收
                     · 逻辑层：必须构造出触发条件，写日志证伪
⑤ 小步改          → 一次只改一个关注点；改动前 svn status 看清工作副本状态
⑥ 自测            → 用该模块文档的「调试手段」表；优先用现成开关/日志锚点，别加临时探针
⑦ 验证            → 按该模块的「验证/自检」表逐项过，拿到可判定的证据（日志原文/数值）
⑧ 提交            → svn；提交信息写"改了哪个模块的哪个点 + 验证结论"
```

**▍ 0.3 环境红线（踩了会浪费时间或造成污染）**

| 红线 | 说明 | 正确做法 |
|---|---|---|
| **rg 静默失效** | 本机 ripgrep 对**明明存在**的字符串也返回无匹配 | 一律 `grep -rn --include="*.cs" '关键词' .` |
| **126 个 `.cs` 是 GBK 编码** | 集中在 `Game/BattleProtect/**`、`scene/world/**`（`WorldTileFactory` / `WorldTileSecretMgr`）、`WorldTileMap/NewVersion/**`、`InnerMap/data/MapDataManager.cs` 等。UTF-8 工具会把它们判成 binary **读不出内容** | 用支持 GBK 的编辑器打开/保存；**不要**用 UTF-8 脚本批量改写（会把乱码固化） |
| **无 git，用 SVN** | 老工程；不要在这台机器上初始化 git | 改动前 `svn status` / `svn diff` 确认范围，只提交自己改的文件 |
| **单文件过大** | `WorldMapView2`(6 032) · `ThroneTile`(3 341) · `MinimapView`(3 553) · `GuideController`(3 078) · `PayController`(1 117) | 改前先 `grep -n` 定位方法边界，别整文件重排/格式化 |
| **插件化多品牌** | 同一份代码按品牌走不同分支（`CCCommonUtils.IsRedAlert()` / `isGtaGang2()` / `＃if RED_ALERT`） | 改表现前先确认**当前构建的品牌**走的是哪个分支，否则会"改对了另一个品牌" |
| **企业文档加密（DLP）** | 本机非白名单进程写的 `.h/.c/.cpp` 会变密文头。本项目是 C＃，**当前未发现受影响文件** | 若将来加 NativeCode 插件，注意 NDK/CMake 产物可能被加密 |

**▍ 0.4 通用验证手段总表**

| 手段 | 怎么用 | 适用 |
|---|---|---|
| **日志锚点** | 每个模块文档的「调试手段」章节给了日志关键词（如指引的「未寻找到」、活动的「活动表异常」、计费的 `add order cache`/`purchase history redo`） | 全部 |
| **功能开关** | `CCCommonUtils.checkIsOpenByKey("key")`：`world_level_view`、`alliance_territory_system`、`open_payment`、`certification_pay`、`dark_guidance` 等。**很多"功能没反应"是开关没开** | 全部 |
| **跳过类开关** | 指引 `ArchivedData.Instance.SkipGuide = true`；地形/表现类看各模块的 Debug 组件 | 指引/表现类 |
| **单点重刷而非重启** | 大地图 `updateDynamicMap(点)`；领地 `RequestTerritoryRegion(rect)`；活动 `postNotification(NEW_ACTIVITY_DATA_REFRESH)` | 刷新类问题 |
| **可视化调试器** | 领地区域 `TerritoryDebug.DrawRegions()`；场景/层级看编辑器 Hierarchy 的 13 层 | 领地/场景 |
| **磁盘核对（子流程/脚本产出必做）** | 长任务或脚本产出后，**查磁盘字节数/日志原文**，不要信"已完成"的自述 | 全部 |
| **真机 + 真渠道** | 只有**付费链路**强制要求（见 §三） | 计费 |

**▍ 0.5 改动类型 → 生效条件速查（最容易踩的一条）**

| 改了什么 | 怎么才算生效 |
|---|---|
| 客户端**热更**表（`config/game/*`：guide / guide2 / guideStage…） | 重新拉热更包（或本地替换后重启客户端） |
| DataAtlas 静态表（`ActivityConstructor.json` / `Exchange_page.json` / `PlotGridEvent*.json` / `Field_monster`…） | **重启客户端**（`ActivityGroupManager.Initialize` 之类只跑一次；`GuideConfig` 是首次访问时才加载） |
| 客户端 C＃ 代码 | 重编（编辑器内 Play 前确认 Status 没卡在 Compiling） |
| 服务器下发的数据（礼包、领地、世界点位、军情怪…） | **客户端改不了**，必须服务器配合；客户端只做解析与表现 |
| prefab / 贴图 / 模型 | 对应模块的 LOD/皮肤加载分支可能缓存（如 `CCNodeCache` 白名单），必要时重启 |

**■ 一、指引模块（Guide System）**

> 原理与全部坑见 [[指引模块]]；此处是**操作流程**

**▍ 1.1 典型开发任务**

| 任务 | 落点 | 完成判据 |
|---|---|---|
| 加一步指引（策划为主） | 热更表 `config/game/guide` 加一条（id 8 位数字 / next / area） | 用剪切板跳步能走到该步且手指指对目标 |
| 加一个新触发源（开发为主） | 业务代码 `postNotification(Global.GUIDE_ON_TRIGGER, "guideId")` | 触发后 `setGuide` 打日志看到该 id |
| 加一个触发动作（跳镜头/开门/播 CG） | `controller/Guide/GuideTriger.cs` 加无参 `public void Xxx()` + 配表 `method`/`cartoon` 填方法名 | 该步进入时动作执行；**配错会 NRE** |
| 目标节点在非弹窗视图里 | 配 `condition` = `GuideNodeManager` 里的公有方法名（参数 `object[]{view, areaStr}`） | 轮询能取到节点，不再 7.5s 超时 |
| 改一步步的存档粒度 | 配 `mark`（非空且非 `"1"` 时以该值存档） | 中途退出后从该步恢复 |

**▍ 1.2 加一步指引的标准流程**

```text
① 先确认"那个时刻目标界面一定会打开"，且节点名与 FairyGUI 组件名一致（区分大小写）
     ⚠️ 配错的代价：轮询 0.15s×50 次 = 7.5s 后 中断整条指引（LogError "未寻找到"），玩家看不到任何提示
② 配 guide 一条：id(8位数字) / next / area = 视图类名_节点名
     ⚠️ id 必须是纯数字：切步时 stopActionByTag(atoi(id))，非数字会变 tag 0 撞车
③ area 的视图解析规则：默认取"当前打开的弹窗"，要求类型与反射出的类一致；
   5 个特例单例（UIComponent / DungeonMainUI / AllianceFortTile / TerritoryBannerTile /
   TerritoryFactoryTile / VillageTile）按 area 字符串包含判断
④ 界面不在弹窗体系里（如世界地图上的地块）→ 不要去猜 area，直接写 condition 方法
⑤ 本地验证三件套：
     · 剪切板放 guideId → GuideKeyCommand 调试指令跳步
     · 场景放 GuideSocket 勾 ShowLogInConsole → 每次 setGuide 打 "current guideId"
     · 数"未寻找到"日志：出现即说明该步节点定位失败
⑥ 调完必须清进度档：跳步会 saveCurrentStepToLocal（本地 key "{uid}_GuideStep" + 服务器 GUIDE_STEP 双写），
   不清会污染后续新手流程
```

**▍ 1.3 排查流程（症状 → 查什么）**

| 症状 | 依次查 |
|---|---|
| 引导完全没反应 | ① `ArchivedData.Instance.SkipGuide` 是否为 true；② `GuideConfig.Get(id)` 返回了**全局共享空 Guide**（表里没有该 id 也**不报错**）；③ 是否走的是另一套系统（`GuideController` vs `REDALERT.GuideNewController`，按品牌二选一） |
| 走到某步卡住 | 该步 `area` 对应的界面此刻是否真的打开、节点名是否与 FairyGUI 一致；日志找"未寻找到"；必要时改 `condition` |
| 引导乱跳/提前结束 | `checkUserAction` 是 **`area.Contains(通知值)` 子串匹配**——业务侧发 `GUIDE_INDEX_CHANGE` 时**必须发完整 area 值**，发短串（如 `"Shop"`）会误触发 `HeroShop_xxx` 的步骤 |
| 进某步就崩 | `cartoon` 配的方法在 `GuideTriger` 里不存在（NRE）；启动期无任何校验 |
| 弱机/弱网随机中断 | 7.5s 是硬阈值；依赖大界面加载的步骤建议拆成前置 `lag` 等待步 |
| 引导表加载失败→全崩 | 热更包不完整导致 `config=null`，之后所有 Get 都 NRE。**每次热更发布后必验首步引导** |

**▍ 1.4 红线**

1. **三处字符串反射**：`area`（视图类名）· `method`/`cartoon`（GuideTriger 方法名）· `condition`（GuideNodeManager 方法名）——**代码改名必须同步改表**，且无启动期校验。
2. **新增触发源走 `GUIDE_ON_TRIGGER` 通知**，不要往 `GuideController` 里加监听（它已注册 20+ 事件，且是常驻单例）。
3. `GuideConfig` 静态构造依赖登录信息选表分支（`guide` vs `guide2`）——**引导表在登录前被任何代码提前访问会锁定错的分支**，别在编辑器里预加载。
4. `GuideController.onEnterFrame` 是 0.1s 永久轮询（常驻开销），不要在引导里做重活。

**■ 二、活动模块（Activity ToolKit）**

> 原理与全部坑见 [[活动模块]]

**▍ 2.1 典型开发任务**

| 任务 | 落点 | 完成判据 |
|---|---|---|
| 已有组内加一个活动 | 配 `ActivityConstructor.json` 一条 + 写 Manager | 启动日志无"活动表异常"；入口能打开 |
| 加一个新活动组 | 上面的 + 写 BannerView + **两处映射表都加** | 该组所有活动点击都不崩 |
| 改展示/锁定条件 | Manager 覆写 `Show` / `Lock` / `LockTip` | 开关关/条件不满足时按预期 FlyTip |
| 新增红点/打点 | Manager + BannerView（基类已接刷新通知） | 红点数与打点上报正确 |

**▍ 2.2 新增一个活动的标准流程**

```text
① 配表 ActivityConstructor.json：
     { "id": "MyActivity", "group": "Welfare", "priority": 15,
       "template": "MyActivityManager", "data": ["参数1"] }
     · template = 类名，不带命名空间（代码会拼 "DayZ." 前缀反射）
     · priority 越小越靠前（组内升序）；同组要错开，相同值排序不稳定
     · data 是字符串数组，Manager 内自行解析（空数组合法）
② 写 Manager（三要素缺一不可，否则启动 LogError + null 入列表）：
     · namespace 必须是 DayZ
     · 继承 IActivityItemManager（注意它是抽象基类，不是接口）
     · 有无参构造
     实现 Init(id, priority, data) / Show / Lock / LockTip / CheckItemKey / ParseRewardPreview
③ group 是**已有组** → 到此为止，启动时 Initialize 自动反射实例化，无需改注册代码
   group 是**新组** → 还要：写该组 BannerView（继承 BaseBannerView，带静态 Create(bannerKey, subKey)）
     + **两处映射表都要加**（ActivityView.cs:77 `viewGoFunc` 与 :92 `groupCloseMap`）
④ 生效条件：DataAtlas 表**改完要重启客户端**（Initialize 只跑一次）
⑤ 验证：
     · 启动日志扫 "----------活动表异常"（出现即 template 类名/命名空间错）
     · 入口点开 → 列表按 priority 排序正确 → 点条目能进子界面
     · 关开关/条件不满足 → FlyTip 文案正确
⑥ 红点与刷新：跨天刷新由 GameController 延时块触发 NEW_ACTIVITY_DATA_REFRESH（注意注释写"两分钟"实为 5 分钟）；
   在编辑器里想立刻看效果 → 手动 postNotification("NEW_ACTIVITY_DATA_REFRESH")
```

**▍ 2.3 排查流程**

| 症状 | 依次查 |
|---|---|
| 活动点不进去、无反应 | ① `GetActivityItemManagerWithKey(bannerKey)` 是否命中 `CheckItemKey`；② `Show` 是否为 false（默认走 `FunctionOnController.CheckFunctionShow`，看功能开关表）；③ `Lock` 是否为 true（会 FlyTip `LockTip`） |
| 点活动**直接崩** | `viewGoFunc` 缺该组映射（`KeyNotFoundException`）。对照 `ActivityView.cs:77` 白名单；**当前配置 12 组、映射表只有 11 组（缺 `Single2`），groceryStore2/3 相关跳转必崩** |
| 启动报「活动表异常」 | `template` 类名大小写/命名空间（必须 `DayZ`）/无参构造/是否继承基类，四者之一不满足；且该活动会**以 null 进列表**，后续遍历可能 NRE |
| `GetActivities(group)` 抛异常 | 组名拼错（字典直取，不返回 null）——先从配置取组名再打日志 |
| 活动到期界面没关 | `OnActivityEnd` 被整体注释（`BaseBannerView.cs:349-354`），已打开界面不会自动刷新/关闭，需手动重开 |
| 换皮项目行为不一致 | `ActivityConstructor` 是 DataAtlas 表，各品牌环境表内容不同——先确认当前环境读的是哪份 |

**▍ 2.4 红线**

1. **配新组名 = 必崩**（除非同 PR 加上映射表两处）。
2. **id 全局唯一**：重复 id 在 Initialize 里直接抛 `ArgumentException`（启动崩溃）。
3. 活动入口字符串（`ActivityView.Create("HeroShop")` 之类）**散落在 QuestGoRegister / FunBuild3D / DailyActiveController 等处**，活动改名要全项目 grep。
4. **GoldExchange 组（49 条）走商城计费**：动这些条目必须联动验证计费链路（见 §三）。

**■ 三、商城计费模块（Pay / GoldExchange）**

> 原理与全部坑见 [[商城计费模块]]；**这是资金链路，操作流程与其它模块不同**

**▍ 3.1 典型开发任务**

| 任务 | 落点 | 完成判据 |
|---|---|---|
| 新增礼包 | **服务器配置** + 客户端 `show_type`/`type` 对齐；页签配 DataAtlas `Exchange_page.json` | 礼包出现在正确页签，价格/限购正确 |
| 改价 / 新商品 | `GoldExchangeItem` 的 `product_id` / `product_id2` / `product_id3` 三件套 + JoySDK 后台 | 收银台显示正确商品与价格 |
| 业务侧发起购买 | `PayController.getInstance().callPayment(item, "来源视图名", callback)` | 走完预校验→收银台→回调 |
| 接入新渠道 | `getCountryCode` 的映射 + `addOrderCache` 的平台字符串 + 补单分支 | 新渠道下单、回调、补单三条链都通 |
| 排查掉单/重复扣款 | 订单缓存 `COKPurchaseInfoList` + 服务端 orderId | 能区分"真掉单"与"客户端展示问题" |

**▍ 3.2 新增/改动礼包的标准流程**

```text
① 服务器侧配置礼包（购买次数、限购、价格由服务器权威下发）——客户端没有这份数据的决定权
② 客户端对齐字段：show_type / type（1 普通 2 促销 3 限购一次）；页签归属配 Exchange_page.json
③ 三件套 ID 配全（最易混淆，漏配直接导致收银台无商品）：
     product_id   = chargeId（计费点 ID）+ 国家码查询 + 预校验
     product_id2  = 订阅商品 ID（bRegister=true 时替代 product_id）
     product_id3  = SDK 实际购买的商品 ID（gameInfo.ProductId；为空则走旧版兜底）
   三者必须与 JoySDK 后台商品配置对齐；product_type：0 消耗品 / 1 订阅
④ 价格字段：dollar（美元）/ price（MoneyAmount 上报）/ gold_value（钻石估价）/ usd_dollar、cdollar（区域价）
   展示文案统一走 PayController.getDollarText（dollar=0 显示"免费"，RTL 与越南版格式不同）
⑤ 功能开关：open_payment（总开关，关掉=全商城不可购）、certification_pay（CN 实名，未实名在付费前拦截）、
   wechat_exchange（微信兑换）
⑥ **验证必须在真机 + 真渠道**（至少 Google 沙盒），四分支一个不能少：
     预校验 → 收银台 → 取消 / 成功 / 杀进程 → 杀进程重进补单

```

**▍ 3.3 排查流程**

| 症状 | 依次查 |
|---|---|
| 收银台没商品 / 价格错 | 三件套 ID 是否配全并与 JoySDK 后台一致（尤其 `product_id3`） |
| 充值不到账 | `PaymentCommand` 票据核验是否成功（核验是**另一条异步路径**，客户端 SUCCESS 回调会先伪造成功）；查 `COKPurchaseInfoList` 待核验订单 |

| 日志线索 | `add order cache` / `remove order cache` / `purchase history redo` / `doPayGoogle receive: code`；打点 `trace_event_pay`、`PayRecordCommand` |

**▍ 3.4 红线**

1. **付费改动必须在真机真渠道走完整链路**，编辑器/模拟器的"成功"不算。
2. **已知 4 条资金级缺陷在改这块前必须知道**（详见该模块 §五 🔴）：支付重入防护被注释 · CANCEL 回调条件写错 · SDK SUCCESS 即伪造成功结果 · 订单缓存去重条件写反（一条脏数据会永久污染整个补单链路）——**任何涉及订单缓存的改动都要先确认这几条是否已修**。

4. 越南版二次确认只对 `RED_ALERT_VI` 生效，**合规逻辑勿外移**。

**▍ 4.2 新增一个场景的标准流程（8 步）**

| 症状 | 依次查 |
|---|---|
| 切场景没反应（请求被丢） | `gotoScene` 的"Y 偏移早退"：`scene.getPositionY() != 0` 时只归零就 `return`，**请求被丢弃、`completeAction` 永不执行** |

**▍ 8.1 动这块之前必须知道的三件事**

1. **四档不是三档**：`level_1`(≥0.40) / `level_2`(≥0.20) / `level_3`(≥0.05) / `level_mini`(其余)。
2. **切档 = 换一整棵子树**：level_2/level_3 会把 `m_layers` **整层关掉**（含城点 `WM_CITY`、行军线 `WM_ROAD`、地表 `WM_TILE`），改由 `secondMapCityRoot` / `third*Root` 顶替 → 三套**完全平行**的内容 + 三套数据（`WorldCityInfo` / `WorldCityInfoSecond` / 三级同构）。
3. **`viewLvl` 是服务器回包字段**，客户端不能指定要几级数据；回包档位不符会**整包丢弃且不补发**。

**▍ 8.2 标准操作流程**

```text
① 改之前先跑一遍自检表（该文档 §四 的 10 个观测点），把当前各档实际状态记录下来当基准
② 明确你要改的是哪一层：
     · 档位阈值          → Global.cs:2831-2834（注意没有 level_1 常量，且 level_4 注释是错的）
     · 每档显示什么      → WorldMapView2.showAllLayer:741-764（唯一的层显隐入口）
     · 单对象的档位表现  → 监听者各自处理：MapPiece.LoadObjects / MapTerritory.SetBoldType /
                           LodTerritoryLine.UpdateWidth / WorldMapLodListener（切 lods[]）
     · 请求策略          → World3DMapDynamicTiledMap.updateDynamicMap:596 起 + activeMinimapCache
③ 改完逐档复测（level_1 → level_2 → level_3 → level_mini 各停 2 秒，再放大回 level_1）
④ 重点确认三件事：
     · level_mini 的行为（当前是"哑档"：不切层、不广播、不请求——**注意它和 level_3 的语义在不同子系统里不一致**）
     · 切档瞬间是否有空白窗口（只有 level_2 有 50×50 区域缓存兜底）
     · 快速来回缩时是否有丢包（`:1294`/`:1315` 的"档位不符即丢弃"）
⑤ 回归：改完后必须重跑 [[联盟领地与王座争夺]] 的领地自检（三级领地是**独立一套**渲染链）+
   确认行军线在 level_2/3 的可见性符合预期
```

**▍ 8.3 排查流程**

| 症状 | 依次查 |
|---|---|
| 缩到最小后地图内容错档 | `MapLevelChange` 的 `level_mini` 分支是空实现（`:775-777`）；HUD 也会停在 `Outer_Map3` |
| 关掉 `world_level_view` 后缩放没反应 | `setScale` 的开关判断在**改档位之后**才 return（`:383-385`），标志位没置 → 不请求不重算（`:310-313` 直接 return） |
| 切档后空白一段时间 | `MapLevelChange` 先切可见性再发请求（顺序问题），且只有 level_2 有本地缓存兜底 |
| 二/三级地图没有行军线 | `m_layers[WM_ROAD]` 被整层关（`:744-751`）；同时查独立开关 `showMarchNodes(bool)` |
| 三级地图地表/领地不对 | 三级走**独立链**：`ThirdMapGroundManager`（209×209）+ `ThirdMapTerritiryManager`/`MapThirdTerritory`；数据走 `WORLD_MAP_LEVEL_THIRD_UPDATE` |
| 来回缩后数据不出现 | `viewLvl` 不符时整包丢弃且不补发；下一帧请求只由位置/缩放变化或定时器驱动 |
| 「每档内容不一样」但代码没改 | 检查 prefab 上的 `WorldMapLodListener.lods[]`（对象级 LOD 与地图档位共用同一事件源，但**独立配置**） |
| 缩放时面板一直消失 | `setScale` 每次都 `getUI().ClearAllBaseTileInfo()`（`:370-371`） |

**■ 九、跨模块联合操作流程**

改一个"新玩法"往往要动 3~5 个模块。以下是四个最常见的联合场景，**按顺序做**。

**▍ 9.1 新增一个活动礼包（活动 + 计费 + 指引 + 红点）**

```text
① 活动模块：ActivityConstructor.json 加条目 + 写 Manager（namespace DayZ / 继承基类 / 无参构造）
     若是新组 → 同 PR 加 viewGoFunc(:77) 与 groupCloseMap(:92)
② 计费模块：服务器配置礼包 + 客户端 show_type/type 对齐 + product_id 三件套 + JoySDK 后台对齐
③ 指引模块（可选）：配 guide 步骤定位到该活动入口按钮（area 必须真实可达）
④ 验证顺序：先活动入口能打开 → 再礼包能显示 → 再真机走支付四分支 → 最后引导能指到按钮
     反序验证会浪费大量时间（前面不通后面测不了）
⑤ 提交前扫一遍启动日志：「活动表异常」不能出现
```

**▍ 9.2 新增一个世界地图玩法（大地图 + 领地 + 缩放分级 + 场景）**

```text
① 大地图：WorldCityType 加枚举 → 写 WorldTileXxx → WorldTileFactory.createWorldTile 加 case（GBK 文件）
     要占多格 → 障碍表配同组 g；要跨服 → 注意工厂的 serverId 过滤
② 若涉及联盟归属 → 用 TerritoryMgr 的 API 做校验，别自己算（领地是"面"，与障碍分组是两套）
③ 缩放分级：确认该内容在 level_2/level_3 该不该显示、挂在哪个 root（默认 m_layers 在二三级会被整层关掉）
     → 需要出现在二三级就得挂到 secondMapCityRoot / third*Root 上，或单独一个 LOD 根节点
④ 场景：若玩法是独立场景 → 走 [[场景管理模块]] 的加场景 8 步；若只是地图上的交互 → 不要新建场景
⑤ 验证：level_1 出现 → 逐档缩放到 level_2/level_3/level_mini 确认表现 → 领地归属判断正确 → 进出无残留
```

**▍ 9.3 改付费相关（计费 + 活动 + 指引）**

```text
① 先读 [[商城计费模块]] §五 的 4 条资金级缺陷，确认你要改的路径有没有踩在上面
② 计费链路只走 PayController.callPayment 统一入口（免费/钻石/金砖/真实付费都在里面分发）
③ 活动侧的礼包展示改动 → 联动验证 GoldExchange 组（49 条走计费）
④ 引导若指向付费入口 → 注意硬编码阶梯链与 enforce 遮罩可能挡住弹窗（closeAllPop 慎用 "2"）
⑤ **验收必须在真机真渠道**：预校验 → 收银台 → 取消 / 成功 / 杀进程 → 杀进程重进补单
```

**▍ 9.4 改客户端表（热更 / DataAtlas）的通用流程**

```text
① 先确认这张表属于哪一类（生效时机完全不同，见 §0.5）：
     热更表 config/game/*        → 重新拉热更包
     DataAtlas 静态表            → 重启客户端（部分 Manager 只初始化一次）
     服务器下发数据              → 客户端改了没用，找服务器
② 表改完先自检"被谁读"——用 grep 搜表名（如 PlotGridEvent / ActivityConstructor / Field_monster）
③ 多人协作的表（guide / ActivityConstructor）改前先 svn update 看是否有人正在改
④ 发布后必验：引导首步 / 活动入口 / 礼包展示（这三处是历史最容易因表坏而全崩的）
```

**▍ 9.5 模块间必须联动的点（速查）**

| 改了 A 模块的什么 | 必须联动验证 B |
|---|---|
| 活动礼包条目 | **商城计费**（GoldExchange 组直接调 `callPayment`） |
| 世界地图新增城点类型 | **缩放分级**（二三级地图默认不显示 `m_layers` 内容）+ 障碍分组（占多格） |
| 领地/联盟相关规则 | **大地图**的放城校验（`isAroundCanBuildGrid` 与 `TerritoryMgr` 是两层校验） + 缩放分级（三级领地是独立渲染链） |
| 任何新增界面 | **指引模块**（新界面常是新手指引的目标；且遮罩可能拦截点击） |
| 场景进出流程 | **指引**（场景切换完成是引导触发源）、**活动**（跨天刷新会在场景里执行） |
| 军情/秘境点位 | **大地图**（`WorldTileSecretMgr`）+ **分片显隐**（`MapPiece.SetNodeActive`） |

**■ 十、提交前回归清单**

```text
□ 改动只涉及本需求范围（svn status 逐个确认）
□ 若是配置表改动 → 按 §0.5 确认生效方式，并已重启/热更后验证过
□ 若是新增"类型/枚举/组/场景 id" → 所有注册点都加齐（工厂 switch / viewGoFunc / 场景 switch / hook 表）
□ 启动日志无异常关键词：「活动表异常」「not found」「未寻找到」「territory data」异常值
□ 按所属模块文档的「验证/自检」章节逐项过，拿到**可判定的证据**（日志原文、通过项数、数值），不接受"看起来正常"
□ 按 §9.5 检查是否需要联动验证其它模块
□ 涉及付费 → 已在真机真渠道走完 预校验/取消/成功/杀进程补单 四分支
□ 涉及世界地图/领地 → 已在 level_1/2/3/mini 四档各看一遍
□ 涉及新增 prefab/资源 → 确认 LOD / 皮肤 / CCNodeCache 白名单等加载分支已包含
□ 引导/新手流程若受影响的 → 用剪切板跳步走一遍，并**清掉本地进度档**
□ 提交信息写清：哪个模块的哪个点 + 验证结论（不是"改了一些东西"）
```
