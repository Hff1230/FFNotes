**■ 三、方案详解**

**▍ 3.1 GPU 顶点动画（自研烘焙）**

**原理**：离线用 `AnimationClip.SampleAnimation` + `SkinnedMeshRenderer.BakeMesh` 把每帧每个顶点的**局部坐标**写进一张「顶点贴图」的像素（一行 = 一帧，一列 = 一个顶点），法线另写一张。运行时**不需要骨骼、不需要蒙皮**，VS 里用 `SV_VertexID` 当列号、`_TimeOffset` 当行号，`tex2Dlod` 查表还原顶点位置，再 `* _MaxMeasure + _MinPos` 反归一化。

**烘焙链路**（`GpuAnimation/Editor/BakeBatchEditor.cs`，菜单 `GPUAnimation/BakeAniData`）：

```
Animator + SkinnedMeshRenderer + AnimationClip[]
        │  SampleAnimation(gameObject, t) + BakeMesh(mesh)      // :146-147 / :171-172
        ▼
  收集 minPos / maxPos → measure = max - min                       // :138-164
        │  每顶点归一化 pos=(v-minPos)/measure，Clamp 到 [0,1]      // :179-193
        │  法线 (n + 1) * 0.5 映射到 [0,1]                          // :196-202
        ▼
  顶点贴图 宽=顶点数 × 高=总帧数（每 clip 100 帧）                   // :131-135
        │  SaveTex：Point 滤波 + NPOT=None + maxSize 8192 + 不压缩   // :233-238
        ▼
  <名>_BakedAnims.png / <名>_BakedAnimsNormal.png
  <名>_BakedAnimDatas.asset（minPos/measure/totalFrame/totalVertexNum/clips[]）
  <名>.mat（_VertexCount / _MinPos / _MaxMeasure / _PosTex / _NormalAnimTex，enableInstancing=true）
  <名>.prefab（MeshRenderer 数组 + GPUAnimationPlayer）             // :332-357
```

**运行时链路**（`Scripts/GPUAnimationPlayer.cs`）：

```
Play(name, loop, speed) → SetClip → currentFrame = startFrame        // :118-146
   Update：currentFrame += Time.deltaTime * rate(120) * speed        // :86
           block.SetFloat("_TimeOffset", currentFrame / aniData.totalFrame)  // :105
           block.SetVector("_Color", color) → mesh.SetPropertyBlock  // :106-110
   到 endFrame → loop 回 startFrame / 否则停住；触发 OnAniEndEvent    // :90-104
   关键帧事件：currentFrame >= EventFrame && 同名 → OnAniKeyFrameEvent // :148-158
```

**Shader**（`Resources/Shaders/Unlit_GPUAnimation.shader`）：

```
float x = (float)vid;                                             // 顶点序号当 U
float y = UNITY_ACCESS_INSTANCED_PROP(Props, _TimeOffset).x;      // 帧号当 V
float3 pro = tex2Dlod(_PosTex, float4(x / _VertexCount, y, 0, 0)).xyz;   // :76-79
v.vertex.xyz = pro * _MaxMeasure.xyz + _MinPos.xyz;               // :80
float3 normal = tex2Dlod(_NormalAnimTex, ...) * 2 - 1;            // :83
col *= dot(normalize(normal), normalize(float3(1,1,0))) * _Factor1 + _Factor2;  // :98 伪光照
```

**实测数据**（`CiBaoBuBing`，磁暴步兵）：

| 项 | 实测值 |
|---|---|
| 顶点贴图 | `2855 × 400`，未压缩 RGBA32 |
| 法线贴图 | `2855 × 400`，未压缩 RGBA32 |
| totalFrame / totalVertexNum | 400 / 2855 |
| clips | `Atk 1-100`、`Death 101-200`、`Run 201-300`、`Standby 301-400`，均声明 `frameRate: 30` |
| 单套显存（未压缩） | 2855×400×4×2 ≈ **8.7 MB** |
| 13 套产物磁盘合计 | 28 张 PNG / 24.3 MB（最大 `dongyuanbing_BakedAnims.png` 3727×400 / 1.4 MB） |

**优势**
1. **CPU 成本恒定且近零**：无 `SkinnedMeshRenderer`（无需每帧计算骨骼矩阵 + 顶点蒙皮），无 `Animator`（无需状态机求值）。
2. **drawCall 可合批**：材质开了 `enableInstancing = true`（`BakeBatchEditor.cs:302`），且 shader 有 `#pragma multi_compile_instancing` + `UNITY_DEFINE_INSTANCED_PROP`（`:30-36`），**同一单位的 N 个实例可以用 MaterialPropertyBlock 走一次 drawCall**，逐个实例颜色不同（`Unit.cs:432-437` 用 `SetColor(Color.red)` 做受击染色）。
3. **顶点数由「模型」决定，与动画复杂度无关**：加动画/加关键帧不增加运行时开销。
4. **低端机友好**：不依赖 GPU 骨骼/纹理采样槽，Android 普遍支持。

**劣势**
1. **显存是硬伤**：贴图尺寸 = 顶点数 × 总帧数。`2855×400` 单套约 **8.7 MB 未压缩显存**（顶点 4.36 MB + 法线 4.36 MB），13 套全常驻约 **113 MB**。顶点越多、动作越多、采样越密，显存呈**乘法**增长。
2. **丢失一切骨骼能力**：换装、换皮肤、挂点（枪口/插旗）、骨骼跟随、IK、单帧混合全没有。
3. **动作不可打断/不可混合**：`Play` 是整段切换，无 crossfade，切换瞬间会「跳帧」。
4. **法线是烘焙时的静态结果**：伪光照用固定方向 `normalize(float3(1,1,0))`（shader `:98`），物体转向时反射方向不随之改变（`o.normal` 转了，但假光源方向是模型空间的固定值）。
5. **修改链条长**：美术改一版动作 → 必须重跑烘焙窗口 → 产物是二进制贴图，**无法 diff**（项目无 git，SVN 上每次都是大二进制变更）。

**注意事项（详见第五章）**：时间基准三处不一致、clip 帧区间 off-by-one、UV 非 texel 中心对齐、平台覆盖段 `overridden: 0` 导致 Android 也不压缩。

**▍ 3.4 序列帧动画（帧动画）—— Cocos 遗产**

**入口**：`Assets/DevCodeFM/IF/Common/BAMovieClip.cs`（225 行，`class BAMovieClip : CCSprite`）——把「一串 `Sprite`」用 Cocos 的 Action 系统跑起来：

```csharp
BAMovieClip anim = BAMovieClip.create();                        // :22
anim.setAnimFrames("ui_effect/boom_{0}.png", 1, 24);            // :146 按格式串批量加载
anim.setFPS(24);                                               // :85  钳制在 [12, 40]
anim.setLoopCount(-1);                                         // :76  <0 = 无限循环
anim.play();                                                   // :102
```

**■ 五、注意事项（已知坑，带证据）**

**▍ 🔴 会算错时长/动作错位（影响战斗手感与技能同步）**

**5.1 GPU 动画「三个时间基准」互相矛盾** — `GpuAnimationPlayer.cs` / `BakeAniData.cs` / `BakeBatchEditor.cs`

| 基准 | 值 | 位置 |
|---|---|---|
| 播放器推进用的 rate | **120** | `GPUAnimationPlayer.cs:18` `public float rate = 120.0f;`，`:86` `currentFrame += Time.deltaTime * rate * speed;` |
| clip 声明的 frameRate | **30** | `BakeAniData.cs:63` `frameRate = 30f`；`BakeBatchEditor.cs:276-281` 写入 |
| 每个 clip 实际烘焙的帧数 | **100**（`sampleCount`） | `BakeBatchEditor.cs:36` + `:279` `endFrame = (i+1)*sampleCount` |

→ 后果：`Atk` 实际播放时长 = 100 / 120 ≈ **0.83 s**，而 `GetDuration("Atk")` 返回 `Length/frameRate` = 100 / 30 ≈ **3.33 s**（`BakeAniData.cs:76-79`，被 `GPUAniamtorBase.GetDuration` 使用 — `KingShot/GPUAniamtorBase.cs:91-96`）。**逻辑层按 3.33 s 排攻击节奏，画面 0.83 s 就播完了**，技能/攻击间隔与动画必然不同步。`frameRate` 字段在整个播放链路里**从未被读取**。
> 验证方法：编辑器里给 `BakedAnimDatas` 的 clip 打点，`GPUAnimationPlayer.TestRun`（`:177-184`）逐 clip 播一遍并用秒表对 `GetDuration()` 返回值。

**5.2 烘焙 clip 帧区间相对贴图行号 off-by-one** — `BakeBatchEditor.cs`

贴图第 0 行（`tex.SetPixel(i, currentFrame)` 的 `currentFrame=0`，`:192/:204`）是**第一帧**，但 clip 区间写成 `startFrame = i * sampleCount + 1`（`:278`），即 `Atk` 从 **1** 开始、到 **100** 结束：
```
贴图行:  0   1 ... 99  100 101 ... 199 200 ...
          ↑   ↑          ↑
      真正第1帧  clip声明起点  Atk 的 endFrame=100 → 落在下一 clip 首帧
```
→ 后果：每个动画**丢掉第 1 帧**、**末尾多播 1 帧下一段动画的首帧**（循环时表现为「顿一下/闪一帧」）。
> 验证方法：编辑器播放 `Atk`（1-100 帧）与直接 `gotoAndStop` 到贴图第 0 行对比首帧姿态。

**▍ 🟠 功能缺陷 / 性能隐患**

**5.3 GPU 动画贴图在移动端也不压缩** — `GpuAnimation/Export/*/Textures/*.png.meta`
meta 里 `platformSettings` 的 `Android` 与 `Standalone` 段虽然写了 `maxTextureSize: 2048` / `textureCompression: 1`，但 **`overridden: 0`（未勾选覆盖）**，实际生效的是 `DefaultTexturePlatform` 段的 `maxTextureSize: 8192` / `textureCompression: 0`（未压缩）。而 `BakeBatchEditor.cs:233-238` 烘焙时也主动设成 `Point + NPOT=None + 8192 + Uncompressed`。
→ 后果：`2855×400` RGBA32 = **4.36 MB/张**，加同尺寸法线贴图 → **≈8.7 MB/套**，13 套常驻约 **113 MB**。低端 Android（2-3 GB 内存机型）风险高。**注意：不要简单地压缩**——顶点位置对量化极敏感（见第六章方案 A）。

**5.4 法线贴图被当 sRGB 纹理导入** — `*_BakedAnimsNormal.png.meta:10` `sRGBTexture: 1`
当前工程是 **Gamma 色彩空间**（`ProjectSettings/ProjectSettings.asset:51` `m_ActiveColorSpace: 0`），所以暂时**无害**。但 `Unlit_GPUAnimation.shader:75-79` 对顶点位置写好了 `＃if defined(UNITY_COLORSPACE_GAMMA) ... ＃else pow(x, 1/2.2)` 的分支，**法线却没有任何色彩空间分支**（`:83`、`:175`）。一旦切 Linear 色彩空间：法线先被 sRGB 解码、再被 `*2-1`，光照方向直接错 → 表现为「全模型忽明忽暗」。

**5.5 shader 的顶点查表 UV 未对齐 texel 中心** — `Unlit_GPUAnimation.shader:76-79`
CPU 侧 `_VertexCount` 传的是 `vertexCount - 1`（`BakeBatchEditor.cs:299`），GPU 侧 `x = (float)vid`，UV = `x / _VertexCount` → `vid ∈ [0, V-1]` 映射到 `[0, 1]`，而纹理宽 `W = V`。即采样点落在 **texel 边界**上（正确做法是 `(vid + 0.5) / V`）。Point 滤波下，`vid=0` 取 texel 0 正确，但大 `vid` 处 `vid·V/(V-1)` 会**累积漂移并落到相邻 texel** → 理论上个别顶点会取到「隔壁顶点的位置」，表现为模型上**局部抽搐/尖刺**。
> 判定：**理论风险，建议实测**（`2855` 个顶点时最大漂移约 1 个 texel）。验证/修复见第六章方案 B。

**5.6 帧动画加载失败会白跑一次** — `BAMovieClip.cs:153-157`、`:170-174`
```csharp
var frame = CCLoadSprite.loadResource(str);
if (frame != null) m_frames.addObject(frame);
else frame = CCLoadSprite.loadResource(str);   // ← 失败又加载一次，结果直接丢弃
```
→ 帧图缺失时每次 `setAnimFrames` 都**重复一次全量加载尝试**（IO/图集查找翻倍），且**没有任何日志**，表现为「动画不出来但也不报错」，排查困难。

**5.7 统一管理器只有一条腿** — `SkeletonAnimationManager.cs:15` / `Spine/SpineManager.cs:9-22`
`useDragonBones = true` 硬编码 + `SpineManager` 全部 `return null`。文档/口头说的「Spine/龙骨可切换」在代码里**不成立**；`IFSkeletonAnimation.create` 走的是龙骨专属的原型缓存 `CCNodeCache.GetDragonbonesPrototype`（`IFSkeletonAnimation.cs:31`），即使将来实现 SpineManager 也不能直接复用。

**5.8 帧动画上传路径无池化** — `IFSkeletonAnimation.cs:31-37`
原型命中时只做 `setVisible(true) + setScale(scale)`，**没有重置动画状态/清 track**；`ResetToPool()` 里的真回收被注释掉（`:63-69`）：

→ 复用对象可能**带着上一次的动画进度/皮肤/颜色**，表现为「同一个行军节点偶尔播错动作」。

**■ 六、技术优化方案**

> 每条给出：**做什么 → 预期收益 → 代价/风险 → 怎么验证**。按性价比排序，前 3 条建议优先做。

**▍ 方案 A（最高优先）：GPU 动画显存治理**

现状 8.7 MB/套（顶点 4.36 + 法线 4.36），13 套 113 MB。四条可选手段，**建议 1+3 组合**：

1. **法线贴图降级为可选/压缩**：`_NormalAnimTex` 在 shader 里只用于 `dot(n, normalize(float3(1,1,0)))` 的伪光照（`Unlit_GPUAnimation.shader:98`）——**一个 float 的信息量**。可以：① 直接不用法线贴图，改为材质上一个 `_LightBias` 常量近似；② 或保留但用 `RGB565/RGBA4444` 压缩（法线量化误差只会让明暗略变，不会像位置那样导致形变）。
   → 收益：**-4.36 MB/套（-50%）**，13 套省约 57 MB。
   → 风险：明暗层次变平。**验证**：同一模型开关法线贴图截图对比（游戏机位）。
2. **顶点贴图用 `RGBAHalf`（8 B/px）或通道拆分**：位置已归一化到 `[0,1]`，`RGBA32` 是 8 bit/通道，`RGBAHalf` 是 16 bit/通道。移动端 RGBAHalf 采样比 FP32 便宜且带宽减半。
   → 收益：**-2.18 MB/套**，精度反而提高。
   → 风险：`TextureFormat.RGBAHalf` 在部分老 GPU 需 `supportsHalfTextures` 检查。**验证**：真机跑一遍看是否有顶点抖动。
3. **降 `sampleCount`（烘焙帧数）**：当前固定 `100`（`BakeBatchEditor.cs:36`）与声明 `frameRate=30` 都不等于动作真实长度。改成 **按 `clip.length × 30` 计算**（例如 1 s 的动作烘 30 帧而非 100 帧），并支持「短动作少烘」。
   → 收益：贴图高度按比例下降，**典型可省 30~70%**；顺带修掉 5.1/5.2 的时间矛盾。
   → 风险：快速动作可能抽帧（30 FPS 采样对刀光类动作不够），需按 clip 配置。**验证**：录制慢放对比原 Animator 效果。
4. **`_MaxMeasure` 精度利用 + 顶点贴图宽度对齐**：把宽度补到 2 次幂（如 2855 → 4096）在现代 GPU 上不省显存（未压缩按实际尺寸算），但**能消除 5.5 的 texel 漂移**；真正的省要从「压缩/降帧」拿。

**▍ 方案 B（顺手修）：统一 GPU 动画的时间基准 + 修 off-by-one**

改三处，一次改完：
```csharp
// ① BakeBatchEditor.cs:276-281 — 帧区间改为 0 基、且记录真实采样帧数与时长
aniData.clips[i] = new GpuSkinningAnimClip(
    clips[i].name,
    i * sampleCount,              // startFrame：与贴图行号 0 基对齐（原 +1）
    (i + 1) * sampleCount - 1,    // endFrame：不含下一段首帧（原 (i+1)*sampleCount）
    sampleCount / clips[i].length // frameRate：按真实采样密度写，而非固定 30
);

// ② GpuSkinningAnimClip.GetDuration()（BakeAniData.cs:76-79）保持不变即可自动正确
// ③ GPUAnimationPlayer.cs:18 — rate 不再写死 120，改为按 clip.frameRate 推进：
currentFrame += Time.deltaTime * (curAniClip?.frameRate ?? rate) * speed;   // :86
```
→ 收益：攻击节奏/技能冷却与画面同步（修掉 5.1），循环不再闪帧（修掉 5.2），`GetDuration` 返回值可信。
→ 代价：**所有已烘焙产物要重烘**（13 套规模不大）。
→ 风险：改完后攻速手感会变（原来 0.83 s 播完，现在可能 1 s）→ **需要策划一起过一遍数值**。**验证**：`GPUAnimationPlayer.TestRun` 逐 clip 计时 + 战斗录屏对攻击间隔。

**▍ 方案 C：UV 采样改为 texel 中心对齐（消除 5.5 漂移）**

```hlsl
// Unlit_GPUAnimation.shader — _VertexCount 直接传顶点数（去掉 -1）
int _VertexCount;                                  // = vertexCount
float u = ((float)vid + 0.5) / (float)_VertexCount; // 落进 texel 中心，杜绝边界漂移
float3 pro = tex2Dlod(_PosTex, float4(u, y, 0, 0)).xyz;
```
同时把 `BakeBatchEditor.cs:299` 的 `skinnedMeshRenderer.sharedMesh.vertexCount - 1` 改回 `vertexCount`。
→ 收益：杜绝「个别顶点抽到隔壁顶点坐标」的理论风险（5.5），是**零成本**的正确性修复。
→ 风险：需重烘/重导材质。**验证**：关掉 `Clamp` 检查、放大看模型边缘是否有尖刺（修复前后对比截图）。

**▍ 方案 D：龙骨图集治理（408.8 MB 是最大的一块）**

1. **清账**：按 `AssetBundles/.../SkeletonAnimation/<目录>` 逐个 `_ske.json` 做引用反查（GUID 反查，不要用路径字符串 grep —— prefab 里存的是 GUID），列出无引用目录 → 下线。
2. **按需分包**：把「主界面/常用」与「活动/一次性」的龙骨拆到不同 AssetBundle，活动结束整包卸载而不是常驻。
3. **图集合并**：同界面共用的多个小骨架合并到一张图集，减少 sampler 切换与 texture 绑定。
4. **控制精度**：与美术约定单骨架图集上限（如 ≤1024²，ASTC 6x6），禁止 2048² 未压缩直接进包。
→ 收益：包体/内存直接下降（先清账通常能拿回 20~40%）。
→ 风险：反查漏判会导致运行时丢图。**验证**：清账后跑一遍全界面遍历（可用 [[场景管理模块]] 的界面清单逐屏过）。

**▍ 方案 E：收敛「一个骨骼方案 + 一个抽象」**

- 新需求一律用 **Spine**（官方维护、编辑器好、IK/混合齐全）；**冻结 DragonBones 新增**，只在存量界面继续跑。
- 把 `Spine` 也纳入统一抽象：让业务只调 `ObjectAnimation`/`Unit` 一层 API，**禁止**新的 `GetComponentInChildren<Spine.Unity.SkeletonAnimation>()` / `GetComponentInChildren<UnityArmatureComponent>()` 散落（现有 44 + 11 处）。
- UI 与 3D 两条抽象线合并（或至少在 `Unit` 层给一个 `PlayAnim(string name)` 统一入口，把 `is NormalAnimation` / `is GPUAniamtorBase` 的判断收进基类）。
→ 收益：新人不踩坑（`Live2D` 命名问题一起解决，建议目录改名为 `SpineRes/` 并保留旧路径链接过渡）；未来换方案不改调用方。
→ 风险：一次性重构面较大，建议**新代码先按新约定写**，老代码按模块顺手改。

**▍ 方案 F：把 GPU 动画的「合批」潜力真正吃掉**

现在虽然 `enableInstancing = true`（`BakeBatchEditor.cs:302`）且 shader 支持 `UNITY_DEFINE_INSTANCED_PROP`，但每个单位是独立 prefab + 独立 `_PosTex`（不同模型不能同批）。可做：
1. **同模型同动画合批**（最常见的同屏兵种）：确保它们共享同一个 `Material` 实例（不要 `renderer.material` 派生新材质），`_TimeOffset` 差异走 MaterialPropertyBlock（代码已经是这个路子，`GPUAnimationPlayer.cs:105-110`，✓ 已具备）。
2. **相位错开**：`currentFrame` 初值加一个 `Random.Range(0, clipLength)`，同批小兵动作不同步，观感更自然且**不影响合批**。
3. **`GPUInstance.shader` 复用**：它是纯 albedo + instancing 的模板，可用于战场的静态道具/纯色单位，省一整套贴图。
→ 收益：同屏 drawCall 从 N 降到 1~2（按模型种类数）。
→ 验证：`Frame Debugger` / `Stats` 看 `Batches` 与 `SetPass Calls`。

**▍ 方案 G：色彩空间迁移预案（切 Linear 前必须做）**

如果将来从 Gamma 切 Linear：
1. `*_BakedAnims.png` 与 `*_BakedAnimsNormal.png` 都要把 `sRGBTexture` 关掉（顶点/法线都是**数据**，不是颜色）；`_MainTex` 保持 sRGB。
2. 删掉 shader 里的 `pow(..., 1/2.2)` 分支（`:75-79`、`:167-171`），改用 `UNITY_COLORSPACE_GAMMA` 统一宏或直接不再特殊处理。
3. 重新烘焙全部产物（导入设置变了）。
→ 收益：避免「切 Linear 后单位忽明忽暗/形变」的重大返工。
→ 验证：切到 Linear 后跑一套完整战斗，看单位明暗与形变。

**▍ 方案 H：补上监控与回归手段**

1. 给 `GPUAnimationPlayer.Play` 加未知动画名告警（现在只有 `Debug.LogError`（`:133`），无埋点）→ 变成可统计项，能在测试期抓出「动画名打错」。
2. 给 `BAMovieClip.setAnimFrames` 的缺失帧加一条 `LogError`（同时修掉 5.6 的重复加载），把「静默不出动画」变成可定位问题。
3. 骨骼动画对象池回收时**强制清 track/皮肤/颜色**（修 5.8），并在测试用例里覆盖「同一节点连续播两个不同动画」。
4. 用项目自带的 `ParticleEffectProfiler` + `Stats` 建一份「动画相关指标」基线（drawCall / SetPass / 动画系统 CPU 占比），每次改动画方案前后对比。
