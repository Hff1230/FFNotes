# 听书高亮长期漂移（声音越来越领先高亮）

## 1. 现象（用户真机 2026-10-16）

> 「听书时间越久好像高亮和声音就会出现偏移，慢慢的高亮还在展示上一句声音已经开始下一句了」

即：**声音领先、高亮落后，且随时间累积**（不是每段固定的小误差，是越听越偏）。

## 2. 代码里能对上现象的两个机理（事实 + 待验证的推断分开写）

### 2.1 事实（读码确认）

| 代码位置 | 事实 |
|---|---|
| `BookSpeaker.ets:230` | 每段时长 `segDurMs = bytesToMs(segBytes)`，`segBytes` 统计的是**收到的全部 PCM 字节** |
| `BookSpeaker.ets:615`（`speakCurrent()` 开头） | **每起一个新段就 `pcmPending.length = 0`** —— 上一段还没来得及写进渲染器的 PCM **被直接丢掉，且不记账** |
| `BookSpeaker.ets:897` | 段末推进判据 `played + 120 >= segDurMs`：按「收到的字节」计时，**不按真正播出去的字节** |

### 2.2 推断（**未验证**，要靠下面的数据判）

若每段末尾都有若干块 PCM 在推进判据之后才到（迟到），它们会被下一段开头清掉、永远不播，
但**字节已经被算进上一段的 `dur`** ⇒ 高亮在每段末尾都要多等那段「其实没播的时间」⇒ **逐段累积、方向正是「声音先走、高亮落后」**。

反向的项也在同一处（会互相抵消一部分，不可凭感觉定责）：
- 段末判据的 `+120 ms` 容差 ⇒ 每段**提前** 120 ms 推进（让高亮偏早）；
- tick 200 ms 粒度 ⇒ 每段推进有 0~200 ms 的量化误差（不累积）。

⇒ 方向与大小**必须实测**，不许凭推断改码（本工程已在计时模型上叠补偿翻过一次车：`03 §J`）。

## 3. 取证打点（已落码，零行为改动）

新增三条日志：
- `selfplay drop tail bytes=N approx=Mms total=T` —— 起新段时被清掉的未播字节（`N`>0 即 2.2 的机理成立；`M` 是它换算成的毫秒）；
- `selfplay seg done … skew=S drop=T` —— `skew = 墙钟 − Σ段时长`（本章累计 0 点 = 第一次写 PCM 的时刻）。
  **判读**：`skew` 逐段单调**增大** ⇒ 高亮确实在落后、且速率 = Δskew/Δ墙钟；若 `skew` 稳定不动 ⇒ 漂移不在段级计时，得查引擎/链路；
- 累计基准在 `setChapter()` 复位（换章/重开从 0 起算）。

**落地与取回（2026-10-16 10:2x 已实现并验证）**：
- 上述每行同时写进沙箱文件 `files/tts_diag.txt`（`BookSpeaker.dlog()`，超过 400 KB 自动裁到尾部 200 KB；任何异常都吞掉，绝不影响朗读）。
- 入口：阅读页点屏幕中间 → 底部「听书」→ 面板里 **「分享听书日志」** → 系统分享面板（可另存为 / 直接发飞书）。
- 模拟器实测（10:24）：文件生成 ✅（895 B，含 `seg done … skew=-152 drop=0`、`play i=261 len=7`）、分享面板弹出 ✅（文件显示名「纯阅-听书日志」）。
- ❗**模拟器上 `drop=0`**：段起清队列时 `pcmPending` 都是空的 ⇒ 2.2 的机理在模拟器**不成立**；用户真机上是否成立，正是这次取证要回答的。
  旁证：模拟器上 `stockMin` 每段都是负值（-80 ~ -397 ms）⇒ 段内确有欠载（与「吭哧」同源）。


## 4. 验收判据（取证轮）

1. 同一章连续听 **≥5 分钟**（用户实际感受最明显的那种时长），从日志算出：
   `skew(t)` 的斜率（ms/分钟）、`Σdrop`（ms/分钟）、每段 `played−dur` 分布。
2. 与「用户听感」对齐：把算出的「听 5 分钟偏几秒」跟用户当场描述比一比（不接受「有改善」这类结论）。
3. 只有拿到上面两组数，才允许动码；动码时**一次只改一处**，并先写回退方式。

## 5. 候选修法（先摆着，取证后再定；**现在不做**）

| 候选 | 一句话 | 代价/风险 |
|---|---|---|
| A | 段起不再清队列（上一段尾巴排干再起新段），并把「实际写入字节」而不是「收到字节」作为计时钟 | 改的是计时模型，必须真机验「段间不吃声」；可能影响段末判据 |
| B | 段末推进判据改用 `segWrittenBytes`（真正播出去的） | 若引擎最后一块总是迟到，`written` 会永远追不上 ⇒ 需要兜底超时 |
| C | 只补「被丢字节」的记账（把 drop 加回下一次计时） | 最保守，但它只是把误差搬到另一处，不解决丢音频本身 |
