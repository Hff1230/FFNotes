## 二、测试类型

### 2.1 单元测试（离线门禁 `tools/tts_buffer_selftest.py`）

**目标**：把「闸门决策」的纯逻辑移植成可复算的用例（照 `tools/reader_pos_selftest.py` 的移植法：复制生产逻辑为 Python、纯标准库、纯 ASCII 输出、<5 s）。

| 测试项 | 测试内容 | 优先级 |
|--------|----------|--------|
| UT-001 | 长段：累计 PCM ≥ `START_BUFFER_MS`(300 ms) 时开闸，且**只**在跨过阈值后的那一次开 | 高 |
| UT-002 | 短段：累计 < 300 ms 时不开闸，`type0` 到达即开闸（用 `bytesToMs` 换算，与 `:656-659` 一致） | 高 |
| UT-003 | 闸门未开期间 `segFirstWriteMs` 仍为 0（计时模型不被污染） | 高 |
| UT-004 | 复位：换段（`:609`）/ `release()`（`:283`）/ `fallbackToEngine`（`:875`）后闸门与累计量归零 | 高 |
| UT-005 | 空段（0 字节）不参与闸门、跳过逻辑不回归（`:231-236` 行为不变） | 中 |
| UT-006 | 反向对照：把用例喂给**当前（无闸门）源码**必须报「无闸门」红（证明门禁有牙） | 高 |

**边界条件**
- [ ] 恰好等于 300 ms；299 ms + `type0`；单块就 > 300 ms；单块 < 300 ms 且无后续块
- [ ] `segDurMs = 0`（空段）与 `calibCh` 未标定（首段）两条路径
- [ ] `pcmPending` 在闸门开之前必须持续累积（不得被 `speakCurrent` 的清零误清）

**运行方式**

```bash
python tools/tts_buffer_selftest.py                 # 新增：闸门决策表
python tools/reader_center_selftest.py --expect-green   # 既有：定位算术（必须保持 57/57）
python tools/reader_pos_selftest.py                 # 既有：位置链（必须保持 150/150）
python tools/jsonrule_selftest/run.py               # 既有：引擎
python tools/shelf_selftest/run.py                  # 既有：书架
python tools/voice_selftest/run.py                  # 既有：音色
```

### 2.2 集成测试（真机 + 日志配对）

**目标**：用日志把「段界空隙」量出来，并用听感确认。

| 测试项 | 测试场景 | 判据 |
|--------|----------|------|
| IT-001 | 听 10 分钟，算段界空隙（`fix-plan.md` §1.4-A 算法） | 中位 ≤ 十几 ms；> 50 ms 的条数对比改前显著下降 |
| IT-002 | 段内块间空隙（FIX-001 诊断补丁后） | 「队列空 && `played + 40 < segDurMs`」计数 **= 0**（改前应为 > 0） |
| IT-003 | 提前量分布 | `dur − played` 落在 120~320 ms（预期不变，本方案不动计时） |
| IT-004 | 语速基准 | `rate: … cps` 仍 4~5（明显偏小 = 被拖慢） |
| IT-005 | 段首延迟 | 「点开始朗读 → 首块 PCM 写入」与改前对照，增量 ≤ 300 ms（记绝对值） |
| IT-006 | 高亮不抢跑 | `Reader.ets` 的 `center follow`/`seg done` 时间线：高亮推进不得早于对应段音频开播 |
| IT-007 | 双链路对照 | 扬声器 3 分钟 vs 蓝牙 3 分钟分别记录（当前代码无 `outputDeviceTag`，以用户听感 + 必要时 `bluetooth_service` 的 `a2dp_per` 佐证） |

**取证纪律**
- 抓日志前核对心跳（宿主机时间 vs 日志末行行首时间戳，差 1~2 分钟即流已死，读到旧数据 ⇒ 结论作废）。
- ❗`BookSpeaker` 的日志**不在** `hilog -T reader` 里，且 `hilog -x` 只留十来秒 ⇒ 一律用**后台流式**抓（`hdc -t <ip>:5555 shell hilog > <原生路径>.log`）+「自己的 pid + 行首时间戳」锚定样本。
- 统计一律用脚本按行首时间戳算（中位/最大/超阈值条数），**不许肉眼扫**。

## 三、验收标准

### 3.1 必须通过

- [ ] **用户听感**：同一本书同一音量听 ≥10 分钟，用户明确回答「顿挫消失/明显减轻」（**这是唯一终判**，日志只是佐证）
- [ ] 段界空隙中位数 ≤ 十几 ms，且 > 50 ms 条数比改前下降
- [ ] 段首延迟增量实测 ≤ 300 ms，且数字写进交付说明
- [ ] 高亮不抢跑（IT-006）：不得出现「高亮先于声音」
- [ ] 回归全绿：滚动跟读不劣化、翻页模式正常、空段跳过有效、后台保活无 `9800005`、进度锚正确
- [ ] 离线门禁 `tts_buffer_selftest.py` 全绿 + 反向对照失败（有牙）；既有四道门禁不回归
- [ ] `python tools/check_both.py` 过；装机后 `bm dump` 的 `updateTime` 为本次、包 md5 与文档记录一致（装机后、下一次构建前当场取）
- [ ] 回退路径可执行（备份副本 + 一条命令覆盖回去）

### 3.2 建议通过

- [ ] 段内断粮计数 = 0（IT-002）
- [ ] `rate … cps` 仍在 4~5

- [ ] 功耗/帧率无明显下降（本改动不涉及渲染，若测则先建基线）

## 四、测试建议

### 4.1 扩展方向

1. **测试数据准备**：固定一本「长句逗号多 + 对话密集」的书作为样本；记录改前的段界空隙分布与段长分布（`segs=N maxLen=M avgLen=K`，`:482-483`）作为对照基线。
2. **自动化测试**：把「抓 hilog → 算段界空隙/提前量 → 判定 PASS/FAIL」脚本化（可扩展现有 `tools/reader_pos_smoke.sh` 的骨架），产出机器可读结果。
3. **诊断常驻化**：段内块级 `(sequence, bytes, t)` 日志与「队列空但未播完」计数，建议做成**可开关的常驻诊断**（而不是一次性补丁），否则下次同类问题又只能靠猜。
4. **链路侧测量**：若对照指向蓝牙，记录 `bluetooth_service` 的 `a2dp_per`（阈值与含义见 `references/tts-playback-smoothness.md` §4）；同时评估把 `outputDeviceTag` 诊断恢复（HEAD 有、工作区已删）。
5. **性能/功耗**：段首 300 ms 缓冲对起播延迟与内存的影响（内存目标 PSS ≤40 MB 不变）。

### 4.2 注意事项

- **一次只改一个变量**：先诊断（FIX-001）后主修（FIX-002），各自单独出包；改动叠加则无法归因（上一轮正是这样整批回退的）。
- **不许再上第二条合成请求/预灌水位**：两次真机都劣化（见 `fix-plan.md` §1.6）。
- **不许动计时模型**：`played`/`segDurMs`/`+120` 判据、`segFirstWriteMs` 打点时机都不许顺手改；闸门只决定「何时开始写」。
- **段首延迟必须告诉用户**：500 ms 级的起播延迟是听感问题，不许隐瞒。
- **判据不许放宽**：门禁与判据文件不许为了求绿而修改；基线更新要在所有改动落地并复跑反向对照之后单独做。
