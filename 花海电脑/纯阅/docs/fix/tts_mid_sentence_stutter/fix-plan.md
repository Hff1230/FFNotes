### 1.2 问题描述与**一个必须先澄清的歧义**

用户原话：「听书时一句话中间偶尔有顿挫感」。

❗**代码事实（实测，`BookSpeaker.ets:27` / `:329` / `:338-339`）**：朗读文本在**逗号处就会切成独立的朗读段**——

```ts
const COMMA: string = '，,';
const isComma: boolean = COMMA.indexOf(ch) >= 0;
const cut: boolean = isCloseQuote || isNl || bufLen >= cap || isEnder || isComma || (isSoft && bufLen >= SOFT_MIN);
```

⇒ 用户听到的「一句话中间」**极可能正是两个朗读段之间的边界**（一个长句会被逗号切成好几段）。因此本问题的第一条工作不是改代码，而是**把「段界空隙」与「段内块间空隙」区分开**：

| 现象落点 | 含义 | 对应候选 |
|---|---|---|
| 断点总在**逗号/句读**处（语义停顿处） | 段与段之间没接上 | H1（段界） |
| 断点在**词中间**（语义连续处） | 同一段内 PCM 块之间断粮 | H2（段内） |
| 偶尔出现、位置不固定 | 提前量抖动 ±(120~320)ms 把 H1 暴露/掩盖 | H4（放大器） |

### 1.3 根因假设（**全部标注证据等级；未量之前不许当结论**）

> **2026-10-16 M-001 真机实测后的裁定（详见 §1.8）**：
> - **H1 成立✅**：段界空隙 **p50 = 59 ms**（>50 ms 占 54%、>150 ms 占 8.6%），远高于「十几 ms 正常」门槛 ⇒ **听感顿挫的主战场是段与段的衔接**。
> - **H4 被削弱❌**：提前量 `dur − played` 实测 **p50 = 21 ms / max 120 ms**（不是计划里写的 120~320 ms）⇒ 它就是 tick 粒度（200 ms）下的正常落点，**不能**再当"把空档暴露出来"的放大器。
> - **H2（段内）**：M-001 现有日志看不到（每段只记第一块 PCM）⇒ 仍待诊断包（FIX-001）量 `uf`/`pcmSpan`/`chunks`/`stockMin`。

**H1（✅ 已实测成立，主因）段界零预取 + 合成延迟未被覆盖**
- 机制：`BookSpeaker.ets:585-646`（`speakCurrent`）只在**上一段推进时**才 `eng.speak(seg.text, …)`（`:637`）⇒ 下一段的合成从那一刻才开始；推进链 `:847-848` 是 `this.cur++; this.speakCurrent();`，**工作区没有任何预取**（`grep -c prefetch` = 0，HEAD 是 5）。
- 唯一掩盖延迟的是「提前切段」：`:842 if (played + 120 >= this.segDurMs)` + tick `:818-820 setInterval(…, 200)` ⇒ 提前量在 **120~320 ms 之间随机抖动**，有时盖得住（无缝）、有时盖不住（空档）= 「偶尔」。
- 反证条件：若量出的段界空隙中位数 ≤ 十几 ms，H1 不成立。

**H2（假设）段内零起始水位——「边到边播」，块间空隙就是顿挫**
- 机制：`:755-769`（`onPcm`）**收到一块就 push 并立刻 `pump()`**；`:772-802`（`pump`）一块一块写；`:726-743` 建渲染器时**没有设 `bufferSize`、不用回调模式**（`grep bufferSize` = 0）⇒ App 侧没有任何余量吸收 PCM 到达抖动。
- 历史佐证：HEAD 版本作者自己抓过这个（`git show HEAD:BookSpeaker.ets` 里有 `feed starve n=… seg=… played=… dur=…`，工作区 0 命中），并配 `await r.getBufferSize()` + `renderer buffer bytes=… ≈ Nms`；**当前代码两样都已被删**。
- 反证条件：若每段 `onData` 实际只回调一次（整段一次到齐），H2 不成立。

**H3（假设）写失败静默丢本段剩余音频**
- 机制：`:783` 先 `shift()` 后写；`:788-797` 写失败只 `hilog.error` + `pcmPending.length = 0` + `break` —— **不重投、不重建渲染器**；文件里也**没有** `on('stateChange')` / `on('audioInterrupt')`（grep 均 0）⇒ 渲染器被系统打断时既不记录也不恢复。
- 反证条件：真机日志里没有 `selfplay write fail` ⇒ 本项不成立。

**H4（放大器）推进判据偏早：120 ms 容差 + 200 ms tick** —— **❌ 已被 M-001 实测削弱**（提前量 p50=21 ms / max=120 ms，属 tick 粒度正常落点，不构成放大器；本项不再作为修法依据）。
- `:841-844`：`played = Date.now() - segFirstWriteMs`（**墙钟，非单调时钟**），`played + 120 >= segDurMs` 即切段 ⇒ 提前量 120~320 ms 抖动；它不直接产生空档，但决定 H1 是「盖住」还是「暴露」。
- 反证条件：把「提前量」与「段界空隙」做相关性，若无关则本项只是放大器。

**H5（低置信）`requestId !== this.curReq` 的 PCM 被静默丢弃**
- 机制：`:755-757` 只认当前请求，其它一律 return（不计数、不告警）。若引擎在切段后补发上一段尾部 PCM，衔接处会缺一截。
- 无实测/官方证据，仅按代码写法列为可能性。

### 1.4 复现与判定方法（**本方案的第一步工作**）

**A. 量「段界空隙」——用现有日志即可，不需要改代码**
现有日志两个字段配对即可算出每段真实播放窗口与相邻段之间的空隙：
- `selfplay pcm first seq=%{public}d`（`:762`，本段第一块 PCM 到达，带行首时间戳）
- `selfplay seg done played=%{public}d dur=%{public}d req=%{public}s`（`:843`，推进时刻）

算法（写脚本按行首时间戳算，**别肉眼扫**）：

```
t_首写(本段) = t(seg done) − played
本段真实播完 ≈ t_首写 + dur
段界空隙   = t(下一段 pcm first) − (t_首写 + dur)
判据：中位数 ≤ 十几 ms 算正常；几十~几百 ms = 段界真有断点
```

**B. 量「段内块间空隙」——优先用官方 API（见 §1.7 A1/A2），我们自己的诊断只作交叉验证**
当前每段**只记录第一块** PCM（`:759-762`），后续分块的 `(sequence, bytes, 到达时刻)` 全无日志；`segWrittenBytes`（`:96/:611/:790`）字段存在但**从未被读**。⇒ 已加一套「仅诊断」补丁（`fix-plan` FIX-001，见 §2.3）：
- **官方口径（首选判据）**：每段取 `renderer.getUnderflowCountSync()` 的**差分**（段首记一次、段末再记一次）——差值 > 0 ⇒ 该段内发生过欠载（官方：欠载帧被替换为静音帧 ⇒ 听感为电流杂音/卡顿）。
- **交叉验证**：`renderer buffer bytes=…≈…ms`（容量）、每段 `chunks/pcmSpan/written/stockMin`（分块数 / 首末块跨度 / 真写出的字节 / 字节法估算的最小存货）。
- **关键判读**：把 `pcmSpan` 与 `dur` 对比 —— `pcmSpan ≈ dur` ⇒ **引擎是按实时节奏流式给 PCM**（那么任何抖动都直接变成欠载，必须靠"攒提前量"解决）；`pcmSpan ≪ dur` ⇒ 引擎一次性给得快，顿挫另有原因（写失败丢队列 / 路由切换 / 提前量）。

**C. 「扬声器 vs 蓝牙」决定性对照（用户做，3 分钟，成本最低）**
同一本书同一音量，**先用手机扬声器**再听一段：
- 扬声器不顿挫 ⇒ 问题在链路（A2DP 抖动）而不是 app，继续在 app 侧调收益有限；
- 扬声器也顿挫 ⇒ 继续在 app 侧找。
（历史笔记 `references/tts-playback-smoothness.md` §4 的同一判据；注意当前代码**没有** `outputDeviceTag`（grep 0 / HEAD 1）⇒ 日志里无法客观确认设备类型，只能用耳朵。）

**D. 让用户标注顿挫落点**：请用户再听一段时记一句「断点是在逗号/句号处，还是在词中间」——这一句直接砍掉一半候选（§1.2 的歧义）。

| # | 事实（官方口径） | 对本问题的含义 |
|---|---|---|
| A1 | **`getUnderflowCount()/getUnderflowCountSync()`（API 10）返回「当前播放音频流的欠载音频帧数量」**（累计值） | 这是「段内断粮」的**官方直接证据**：每段取一次差分，>0 就说明该段内真的欠载过 ⇒ 不用再靠我们的存货估算当唯一依据 |
| A2 | **`getAudioTimestampInfo()/Sync()`（API 19）返回 `framePos`（已播采样数）+ `timestamp`（ns）**；官方原文「**已播放的数据量不等于写入数据量**」 | 想要精确「手上还有多少存货」= 已写采样数 − `framePos`；注意调用频率建议 ≥200 ms 一次、`flush()` 会把它归零 |
| A3 | **`write()` 自 API 11 已废弃**，官方推荐 `on('writeData')` 回调；**填不满时务必返回 `INVALID`（系统会再次请求），严禁填 0 数据后返回 `VALID`**——官方原文把「0 数据 + VALID」直接列为卡顿/破音成因 | 我们当前用的是废弃接口 + 「分块随到随写、填不满照写」⇒ 结构上就落在官方点名的风险带上 |
| A4 | **AUDIOBOOK 默认走低功耗渲染器**：亮屏缓冲**最大 1000 ms**、熄屏**最大 10000 ms**；官方建议「一次性填满缓冲区」，且「若应用无法快速提供数据，**会降级为普通渲染器**」 | 缓冲容量本身很充裕 ⇒ 顿挫更可能来自**喂数节奏**（引擎分块到达的抖动）而不是缓冲太小 |
| A5 | **取不到数据时消费端不阻塞、直接填静音帧**：间歇静音帧=电流杂音，大量=卡顿 | 与用户听感「一句话中间偶尔顿挫」一致；也说明**欠载是可被 A1 计数的** |
| A6 | `AudioRendererInfo.content`（含 `CONTENT_TYPE_SPEECH`）**自 API 10 起已废弃**，改由 `usage` 决定 | 我们代码里还在设 `content`（无害但是死字段）；顺手清理要单独出包、不与本轮混淆 |
| A7 | AUDIOBOOK 后台播放**必须**接 AVSession + 申请 `AUDIO_PLAYBACK` 长时任务，否则**静音+冻结**；且不在 `setDefaultOutputDevice` 支持范围内 | 与我们已知的 `9800005` 保活问题同源，本轮不动（已由前序修复覆盖） |

### 2.2 推荐方案（**一次只改一个变量**；§1.7 的官方事实已并入）

**修订后的优先顺序（2026-10-16，API 核实后）**

1. **M-001 + FIX-001 先量（不改行为）**：真机 10 分钟，拿 ① 段界空隙分布（现有日志配对）② **每段 `getUnderflowCountSync()` 差分**（官方欠载计数）③ `chunks/pcmSpan/written/stockMin` 交叉验证 ④ `pcmSpan vs dur`（判断引擎是流式还是整段给）。
2. **按 M-001 实测（§1.8）重排候选（只做一条，单独出包）**：
   - **FIX-002D（首选，治 H1＝段界 59 ms 空档）**：**单段读前**——当前段还在播时就把**下一段**提交给引擎（`queueMode: 1` 排队追加，避免打断当前合成），其 PCM 按 **requestId 前缀严格隔离**存进独立缓冲，**只用于段界补位**（绝不参与 `segDur/推进/高亮`）。⚠️ **这是历史上两次翻车的方向**（症状都是"预取事件混进当前段推进 ⇒ 高亮抢跑/滚屏错位"）⇒ 本单必须满足三个硬条件才许开工：① 前缀身份隔离（预取请求的 `type 0/1` 一律只登记、**永不推进当前段**）；② 不新增定时器、不碰计时模型；③ 有离线门禁与"高亮/滚屏不回归"的真机对照（`center follow` + 截图）。**先写回退方式再动手**。

   - **FIX-002F（诊断侧，零风险）**：把 `uf`/`pcmSpan`/`chunks`/`stockMin` 留成**可开关的常驻诊断**，否则下次同类问题又只能靠猜。
3. **FIX-003 真机验收**：同一本书同一音量 ≥10 分钟（含换章、息屏），用户听感 + `getUnderflowCountSync` 差分双签（判据：**每段欠载差分 = 0**）。
4. **顺手项（单独出包，不与本轮混）**：移除已废弃的 `content: CONTENT_TYPE_SPEECH`（A6）；按官方顺序处理暂停/续播（`Pause → Flush → Start`）。

**影响范围**
