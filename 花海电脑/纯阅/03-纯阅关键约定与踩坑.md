# 纯阅 · 关键约定与踩坑

> 这里每一条都是**用真机事故换来的**。改相关代码前先读，别重新发明。
> 本文 = **红线与口径的唯一来源**；待办与验收判据见 [[04-纯阅待办与验收]]，规格见 [[01-纯阅功能规格]]。

## A. 红线与总口径

1. **任何情况下不许损坏阅读进度**——写库前必须自检，宁可这一次不写：位置三件套（`offset` + `chapterTitle` + `progress`）里任何一个对不上，都按"伪值"处理。
2. **位置锚（三态回退）**：恢复位置时
   ① 章号能从偏移推出、且与记下的章节名一致 → 用偏移（最精确）；
   ② 两者冲突（正文被重排/续抓/换源）→ **以章节名为准**；
   ③ 偏移越界 → 章节名 → 「进度 × 源目录总章数」→ 最后退到记下的章号。
3. **进度的分母用「源目录总章数」**（`srcTotal`），不用"已抓章数"——否则补章后进度会往回掉。
4. **保存前自检（四闸，含 2026-10-14 定案的例外与白名单）**：伪值一律不覆盖库里的好位置。
   - **G1**：自打开以来**无任何用户交互**（`userTouched=false`）→ `saveProgress()` 直接 return，只写日志。
     - **例外（听书）**：**TTS 播放中视为"用户已交互"**（用户点播放即视为授权写入），听书的自动推进/自动跨章位置照常落库；仍走 G3/G4 的伪值检查。
     - 理由：听书无屏幕交互，G1 硬拦会让**听了半小时的进度不落库**（01 §2.4 要求"切章自动接续"）。
   - **G2**：无用户交互期间**不许因滚动推导改 `curIndex`**（只有真人滚过/翻过才认）。
   - **G3**：`!userScrolled` 且 **jumped ≥ 1** 且偏移 ≈ 新章开头（`off == ch.start`）→ 判伪值丢弃（现实现只拦 >1 章，**必须改成 ≥1**）。
     - **白名单（不算伪值）**：位置变化**源于**「下一章 / 上一章」过渡按钮点按、目录/书签/进度条跳转、听书自动跨章时，`off == ch.start` 属**正常**。
   - **G4**：`placing` 期间（落位未收敛）**禁止写库**；退出时若仍在 `placing`，按"最后一次已确认的 `offset`"写。
5. **落库时机**：`aboutToDisappear`（退出阅读页）**不够**——用户直接回桌面/切走不会触发。必须三条一起：
   ① `EntryAbility.onBackground` 打 `AppStorage.setOrCreate('appBgTick', Date.now())` 心跳 → 阅读页收到立刻写库；
   ② 阅读中滚动/翻页停稳 ≥8 秒节流落库；
   ③ 退出阅读页时写库并**等写库完成再通知书架刷新**（否则书架读到旧进度，再把旧偏移写回去＝撤销改动）。
6. **「从头开始」必须先清零写库再进阅读页**（只改内存副本会被退出保存覆盖）。
7. **用户主动跳转**（目录/书签/进度条）要标记 `userScrolled=true`，否则会被自检当伪值拦掉。

## B. 装载（打开书）

- **必须分片**：2MB 分片读 → **流式解码**（`decodeToString(data,{stream:true})`，跨片的半个汉字由解码器拼）→ 逐片 `normalize` → 最后 join。
  老路（整本 readAll + 整本 decode + 链式 4 次 replace）峰值约 85MB，而且**只有分章阶段报进度** ⇒ 走索引缓存时百分比全程 0%（用户报"卡在 0%"）。
- **流式解码要先探**：老 TextDecoder 不认 `{stream:true}`，分片解会把汉字截成乱码 → `supportsStreamDecode()` 探一次，不支持就回退整本解码。
- **跨片的 `\r\n` 不能拆**：每片末尾若以 `\r` 结尾，把它留到下一片再合并清洗。
- **丢 0 填充**（`dropNulBytes`）**只能在非 UTF-16** 上用（UTF-16 的 ASCII 每字符都带 0x00）。
- **章节索引 sidecar**：`<书文件>.idx`，校验 `文件字节数 + 正文字符数`，文件变了自动失效（抓取追加后重扫）；后续要扩成「每章字节区间 + 块索引表」（见 [[02-纯阅工程与架构]] §2）。
- **单章封顶**（`MAX_CHAPTER_CHARS`）：遇到"一整章几百万字"（伪正文）按行切「（续 N）」，否则分页卡死 + 渲染 OOM。
- 装载/分章/分页都不要整本同步跑（会触发系统 `THREAD_BLOCK_3S`，用户看到"白板半天不动"）。
- **目标（未完成，判据在 04）**：正文不许整本常驻。装完 37MB 的书现在仍有 ~148MB PSS（arkts 堆 78.8 + native 52 + 65MB 被换到 swap），目标 ≤40MB —— 做法是"当前章 ±3 章窗口从磁盘读"（`.idx` 补每章字节区间）。

## C. 位置落位（打开书后回到原处）

- 打开瞬间 List 还没铺数据，此时 `scrollTo/scrollToIndex` 会被忽略 ⇒ 必须等真实可滚范围 > 0 再落位。
- `scrollToIndex` 在懒加载 + 块高不一的列表里**落点会偏**（未测量的块只能估）⇒ 用**像素滚动 + 自校准**：真实内容高 ÷ 估算内容高 = 比例，把估算像素换成真实像素，落位后读回第一块核对，不齐继续收敛。
- **收敛必须有上限**：现为 40 次（实测出现过「位置落位放弃：attempt=41」，空转 1~2 秒白卡、位置还会游走 off 4877→2765）⇒ **收到 3~4 次**，不齐则用估算兜底并把该次落位标记为"未精确"。
- 落位期间不要换章、不要存进度（`placing` 标志，配 A-4 的 G4）。
- **作用域变更（2026-10-14 定案：上下滚动改「按章切换」）**：列表一次只装**当前章**的块 ⇒
  - 「像素滚动 + 自校准」作用域从「全书」缩到「**单章之内**」，比例分母是**本章**估算内容高，误差量级随章内块数下降；
  - **章号由"当前章"状态直接给出，不再从像素推导**；
  - **逐块估算高度这一根因不变** ⇒ 仍按 FIX-002（位置来源改可见项索引）/ FIX-002b（`keyGenerator` 稳定化 + 同源块高）处理；
  - 落位失败也不许在无交互期改写 `curIndex`（A-4 的 G2）。

### C.1 滚动模式三个「看起来像玄学」的坑（2026-10-14 定案，均已修）

1. **页码胶囊恒显示「本章第 1 页」（用户报：始终 1/11）**
   根因：窗口一次装 ≈20 章连排，`currentOffset()` 算出的全局偏移落进**别的章**时会被夹回 `curIndex` 章的区间 → 章内页码恒为 1，总页数还是当前章的 →「1/11」。
   修法：滚动模式窗口**只渲染当前章**（`windowRange()` 恒 `[center,center]`）。**别再恢复多章连排**，否则这个 bug 必然复发。
2. **滚着滚着直接跳章（用户报：滚动模式直接滚到第四章了）**
   根因：`maybeShiftWindow()` 在滚动模式也会「按视口顶部所在章换窗口」，等于自动换章。
   修法：滚动模式该函数**直接 return**；换章只由章首/章末按钮、目录/书签、听书驱动 —— 一章滚到底**自然停住**（`EdgeEffect.Spring`）。
3. **切章后页码还留着上一章的数字（1/23 出现在章末）**
   根因：`updatePageLabel()` 在切章那一刻就算过一次（此时 `pageStarts` 还是旧章、滚动还在顶部），而 `pageLabel` 值没变化 ⇒ 之后没人再刷新它。
   修法：`gotoChapter()` / `gotoOffset()` 里**延后 300ms** 强制刷一次。凡「先改状态再等布局」的位置类显示，都要按这个套路补刷新。

4. **切章后停在「半中腰」，看不到本章最上面（用户报）**
   根因：**`LazyForEach` 数据源变化时，List 的滚动偏移不会被框架重置** —— 切章那一瞬它沿用上一章的偏移量（实测 `curY=8026 off=13661`，正落在新章中间；新章更短时被夹到新章 `maxScroll`）。
   而原来只靠「位置落位」把它纠回 0，**落位在用户手动滚动过之后会放弃**（`位置落位放弃`）⇒ 纠不回来，就成了用户看到的现象。
   修法：`settleChapterScroll(toEnd)` —— 切章后 300ms（数据提交完）**自己补一次 `scrollTo`**（章首→0、章末→`maxScroll`）＋ 刷页码＋刷高亮，**不依赖落位是否成功**。
   ⚠️ 凡「换数据源后要回到顶部」的列表，都要显式补一次定位，别指望框架或落位。

### C.3 听书（TTS）的三个坑（2026-10-14 定案，均已修）

1. **听书时「屏幕内只显示一句」** —— 不是渲染 bug：**听书设置面板没收起**，面板霸占下半屏（页模式还会按 `blockedH()` 把分页高度一起压掉）。
   修法：点「开始朗读」后自动 `panel = ''` + `ttsPanelVp = 0`（@Watch → `onPanelHChanged` 重分页/重算高亮），正文恢复满屏。
2. **高亮比声音早一句（用户报「高亮的是下一句」）** —— 同一次 `speak` 会回调**两次**：`type 0 = 合成结束`（PCM 刚生成、音频还在播）、`type 1 = 播报结束`。旧代码不做 type 判断、只按 `requestId` 去重 ⇒ **合成一结束就 `cur++`**，高亮抢先跑到下一句。
   修法：`type 0` 只登记兜底定时器、**不推进**；`type 1` 才推进。
3. **兜底**：真机上「播报结束」偶发不来（旧注释：有时只给其中一次）⇒ 收到 `type 0` 时按「字数 × 每字耗时（1x ≈ 4 字/秒）」估时长挂定时器，到点仍没等到 `type 1` 才推进 —— **宁可晚一点，不许抢拍**，也不能把听书卡死。

⚠️ 自查日志：正确顺序是 `BookSpeaker: seg synth-done(不推进) pure_N` 紧跟 `seg done pure_N type=1`；只有前者、既没有后者也没有 `synth fallback 推进` = 卡住了。

### C.4 朗读断句（TTS 分段）三级规则（2026-10-14 定案）

用户口径："按句号分割的话，一句话可能太长；普通的逗号、省略号可以单独拆；**但是双引号中间说的话不要再拆**。"

| 级别 | 规则 | 原因 |
|---|---|---|
| ① 一级 | 句末标点（`。！？…；`）/ 换行 | 自然断句 |
| ② 二级 | 累计 ≥ `SOFT_MIN`(24 字) 时，在句中停顿标点（`，、：`）处喘口气 | 按句号分会出现几十上百字的段：TTS 请求长、暂停迟钝、**高亮粒度粗、跨页判断也跟着变粗** |
| ③ 硬上限 | `SEG_MAX` 90 字（引号内 150 字） | 无标点长串兜底；引号内放宽以免动对话 |
| ★ 引号 | **开引号本身就是断点（对话自成一段）**；**短对话整段不拆**；**超长对话照切**（句末 ≥45 字断、逗号类 ≥70 字断，引号内硬上限 120 字） | 落实「双引号中间说的话不要拆」，同时满足「遇到超长的段落或超长的双引号，也要用逗号、句号切成小句」 |
| 收尾 | 「只有标点的段」（如闭引号后剩下的「，」「……」）并进上一段 | 别让 TTS 念一个孤零零的逗号 |

⚠️ 高亮粒度 = 段粒度：二级断句会让高亮在一句话内**逐小句推进**（跟读更细），不是 bug。
**实测（`剑来` 前 50 万字）**：段数 13442 → 19414；最长 110 → 152（超长对话安全阀）；平均 28.1 → 24.4；**超过 40 字的段 26% → 7.8%**；**4348 段引号对话中 0 段被意外拆开**（仅 203 段是超过 150 字的超长对话，属安全阀）。真机自检日志：`BookSpeaker: segs=N maxLen=M avgLen=K`。

### C.5 听书跟随的两种「不跟」及修法（2026-10-14）

1. **翻页模式：一句话跨页，屏幕不翻**
   现象：高亮被页底切断，声音已经念到下一页的字，屏幕还停在上一页。
   修法：`followSpeech` 里算 `p`（段首所在页）与 `pEnd`（段尾所在页）；跨页时按**字数占比**决定：占比 ≤50% 立即翻到 `pEnd`，否则按占比估时（`estSegMs`）**念到分界点再翻**（`pageTurnTimer`，换段/停播必须 `cancelPageTurn()`）。
   日志：`page turn: seg=.. p=53 pEnd=55 onP=22 total=97 ratio=23 est=25220` → `page turn done: page=56/150`。
2. **滚动模式：高亮跑出屏幕，屏幕不动**
   根因：可见性判定只看了「**段首**块在不在可视带」，段一长（对话 60~150 字）段首刚在带上沿、段尾早已出屏 ⇒ 判定"已可见"不滚。
   修法：改按**段尾**判定（整段在带内才不滚）；整段装不下时先顶段首，念到后半段再把段尾带进视野（`followTailTimer`，按段内时间估 50% 处触发）。滚动统一走 `scrollToShow()` 并回读校正（`follow check: diff=21`，不累积）。
   ⚠️ 判定用打点：`hrel`（高亮起点块距视口顶像素）、`hrelEnd`（高亮**终点**块距顶像素）、`band`（可视带高）；**0 ≤ hrel 且 hrelEnd ≤ band 才叫"高亮在屏内"**。

### C.5.1 听书跟读「翻页抖动」——同一病根：两个目标打架（2026-10-14 修）

- 现象：翻页模式页码来回跳（实测 `page turn done: 42/89 → 41/89 → 42/89`），滚动模式 curY 在几十像素间抖。
- 根因：**段级对齐**（把页面/视口拉回"本段起点"）与**跟随推进**（按语速预测往前推）目标不同，两边轮流执行。
- 修法（一个目标原则）：
  · 翻页模式：段首对齐只在「当前页已不在本段的页范围 `[p, pEndPage]`」时才执行；段内推进只由 `followFrontier` 驱动，且**只往前翻**（`p > pageIndex`）。
  · 滚动模式：段首/段尾对齐（旧 `followSpeechScroll`）**停用**，统一走 `followFrontier`（滚动分支 = **居中跟读**，见 C.5.3）。
  · 原「按两页字数占比定时翻页」删除（与 600ms 跟随定时器重复，是重复翻页的来源）。
- 判据：翻页模式跑一段听书，`hi diag` 的 `page` 序列**单调不减**，且 `hpage == page`（屏幕页 = 高亮页）。实测 7→7→8→8→9→9→10 全单调。

### C.5.2 滚动模式跟读：为什么最后放弃了（2026-10-14）

- 要求演化：用户先要"滚动模式也要跟着读"，于是做了「按实测语速预测 → 600ms 跟随定时器 → 让正在读的那一行留在屏幕下半区」。
- 连续踩到三个坑：
  1. 判据用「**段落块顶部**」像素 → 正文段落很长（几百像素）时块顶永远在舒适区，而"正在读的那一行"早掉出屏幕 ⇒ **永远不滚**（实测：`hi` 在推进、`curY` 恒定、`follow tick` 0 次）。修法：按**块内字符比例插值**出那一行的真实像素位置。
  2. 段级对齐（把视口拉回段首）与跟随推进两个目标打架 ⇒ 视口/页码来回抖（`42/89 → 41/89 → 42/89`）。修法：一个目标原则，段内只往前推进。
  3. 用户一滚就被定时器顶回去 ⇒ 体感"不让我滚"。修法：**用户优先窗**（碰屏幕后 5 秒内不自动跟随）。
- 结局（**已反转，见 C.5.3**）：2026-10-14 曾拍板「**听书只支持左右翻页模式**，开听书自动切换」；2026-10-15 用户要求改回 —— **滚动模式开听书必须留在滚动模式**（「我们做滚动高亮居中就是为了听书兼容滚动」）。三个坑现在逐条有了对价：坑①（块顶判据滚不动）由 `pixelOfLocal()` 块内插值修掉；坑②（两个目标）由「一个目标原则」+ 居中目标式 `centerTarget()` 统一；坑③（顶回用户滚动）由「听书期间锁手势」消除 —— 听书时用户根本不能滚，就没有「谁让谁」的问题。
- 教训：**"跟随"这种持续抢占视口的自动化，目标和时机必须唯一**；否则多套逻辑轮流执行就是抖。做滚动跟读前先把上面三条当硬约束核对一遍。

### C.5.3 滚动模式「居中跟读」＝ 听书兼容滚动的实现（TTS-B，2026-10-14 落地 / 2026-10-15 定为听书唯一滚动方案）

- **目标**（用户口述）：「在除章节收尾部分的情况下，始终保持当前听读的句子刚好滚动到屏幕中间位置」。
- 目标式（`centerTarget(localFrom, localTo, frontierLocal)`，**居中跟读与切模式落位共用同一式**）：
  · `centerY` = 句块 `top + 句内插值偏移` 的句中点（`pixelOfLocal` 块内按字符比例插值，不用块顶）；
  · **长句**（段高 > `band × CENTER_LONGSEG_FRAC`，如长对白可超一屏）⇒ 改为盯住**正在读的那一行** `pixelOfLocal(frontierLocal)`，否则整句居中会把正在读的字挤出屏幕；
  · `want = clamp(centerY − band/2, 0, maxScroll)` ⇒ **章首/章尾天然夹住**（内容不足半屏时滚不动，不会用空白硬居中）。
- 节奏：跟 `startFollowTick()` 的 600ms 定时器 + 实测语速预测的「当前字」；**死区** `CENTER_DEADZONE_FRAC`（视口 12%，验收判据 15% 的一半）内不动，免得每 tick 动一下发抖；滚动用 `scrollTo + animation:true` 线性平移（**不用** `scrollToIndex` 硬跳）；`onScroll` 里不写任何 `@State`。
- 判据（`hi diag` 打点）：`center|…|dev=` 是「句中心 − 视口中心」的像素偏差，稳定在 **±15% 视口高**内即合格；`hrel/hrelEnd/band` 仍要满足 `0 ≤ hrel 且 hrelEnd ≤ band`（高亮在屏内）。
- 与「听书兼容」的关系：2026-10-15 起**滚动模式听书就靠它**（`toggleSpeech()` 不再 `switchMode(true)`）。前提是听书期间锁手势（D2）——否则自动跟随与用户手滑又是两个目标。

### C.6 后台听书的进度（2026-10-14 用户要求）

- 现象：后台/息屏听了一章，回来位置还在老地方。
- 根因：进度一直用 `currentOffset()`（滚动模式由 `curY/maxScroll` 推）——**后台时视口不给实时滚动值**，它就冻在旧位置；再加上「位置未稳定 + 没用户滚动」的伪值拦截，保存还会被整段拦掉。
- 修法：`speechOffset()` = 章起点 + 当前朗读段偏移（`hiSegFrom`，就是高亮的那一段），听书期间保存**以它为准**；并把 `ttsPlaying` 计入「已交互」，不再被 `posUnsettled` / 伪值检查拦。
- 验证：后台读到 `hi=1219..1246` → 强杀重开 `restore pos: 按偏移 idx=5 第六章 下签 off=19470`（布局值当时冻在 19318，说明存的确实是朗读位置）。
- ⚠️ 打点别糊：`save pos` 那行日志打印的是 `currentOffset()`（布局值），**看不出实际存的是哪个**——后台排查时以「重开落位」为准，或看 `tts=Y` 标记。

### C.7 构建报「Failed to delete ... entry-default-signed.hap」

- 不是权限问题，是**你自己（或别的工具）还开着这个 hap 的句柄**。踩过：用 `zipfile.ZipFile(hap)` 核验包内代码后没关，Hermes 的 python 会话一直占着它 → `hvigor` 删不掉旧包、直接 BUILD FAILED（而且失败得很快，容易误判成"编译问题"）。
- 定位：`python -c "import psutil; [print(p.pid,p.info['name']) for p in psutil.process_iter(['pid','name']) if any('entry-default-signed.hap' in f.path.lower() for f in p.open_files())]"`。
- 规矩：核验包内代码一律用 `with zipfile.ZipFile(...) as z:`（或读完立刻 `close()`）。

### C.8 搜索找书「没找到 + 闪退」（2026-10-14 用户报，真机未复现）

- 现象：搜「枪炮、病菌和钢铁」没结果，并导致 App 闪退。
- 已排除：关键词是**编码过**的（`HttpUtil` 走 `encodeURIComponent`，`、` 会变 `%E3%80%81`）⇒ 不是"URL 里带中文/特殊字符"的问题；没结果本身更可能是站点索引/规则不匹配。
- 本地复现不了（模拟器**没有书源**，公版那条路也没撞出崩溃）⇒ 按"最可能崩的地方"全部堵上：
  1. **异步 UI 处理器必须自带 catch**：`onClick`/`onSubmit` 调 async 方法**没有 catch**，DB 或网络里任何未捕获异常 = ArkTS 未处理拒绝 = 直接闪退。`onSearch()` 已整段 try/catch/finally（`searching` 放 finally，异常也不会卡在"搜索中"）。
  2. **并发限批**：原来把全部书源一次并发抓走，改成**每批 4 个**（和"检测可用性"一致），几十个源同时抓会同时压内存和站点。
  3. **结果上限** 500 条，个别站返回上千条不至于吃光内存。
  4. 每个源的结果/错误都打 `searchsrc` 日志（"源没返回" vs "源报错"一眼分清）。
- **崩溃取证钩子**（`EntryAbility.onCreate`）：注册 `errorManager.on('error', …)`，JS 崩溃会被接住并打 `tag=crash` 的日志（含消息+堆栈）；副作用是**应用不再因 JS 异常直接退出**，症状先止住。⚠️ `ErrorObserver.onUnhandledException` 的参数是**字符串**（消息+堆栈），不是 `BusinessError`（写错会编译报 `No overload matches this call`）。
- 若仍崩溃：从设备拉 `hilog -x | grep crash` 即可定位（需要真机开无线调试）。

## E. 备份到文档 / 导出

- 保存对话框（`DocumentViewPicker.save`）只做两件事：**建一个空文件 + 给 uri**（`file://docs/storage/...`）。
- ❌ `fileIo.copyFile(沙箱路径, uri)` 必失败（`No such file or directory`），用户看到的是"失败提示 + 目录里一个 0B 文件"。

## G. 书源子系统（仅自用版）

- 纯阅规则子集：`class.x/id.x/tag.x/text.x`、`@text/@href/@src/@html/@ownText/@textNodes`、多级 `@`、`||`、`##正则##替换`、`[n]`/`.n`/`!n`。
- **不支持**：`{{ }}` JS、`@js:` 真逻辑、`<js>` 解密 —— 带这些的源纯阅永远跑不了（导入时提示，不要假装能用）。
- **JSON 接口源（2026-10-15 新增，口径见 G.1）**：响应体是 JSON 时走 JSONPath 子集求值器（`@JSon:` 前缀、裸字段名、`$.a.b[*]`、`[n]`/`[*]`、`$..key`、`?(@.key)`、`||`/`&&`、`##正则##替换`、`{{路径}}` 模板插值）。
- 检测语义：只有「解析不了/超时/5xx」才算死源（4xx 是防盗链，不算）；关键词固定「小说」。
- 抓取要克制：每站限速、并发批抓、断点续抓、限流退避；「认书名不认源」，换源只补新章；重复段落有专门处理。
- **抓取正文的整理（2026-10-14 定案）**：抓取路径必须**先提纯再落盘**，并把**未整理的原始正文**写进 `<书>.raw`（否则整理不可回溯）。口径见 [[01-纯阅功能规格]] §2.7。

### G.1 JSON 接口源（JSONPath 子集）—— 唯一口径（2026-10-15）

**为什么做**：池子 4023 源里判「跑不了」的 1377 个中，JSON 接口类 377 个（地址算得出来的 370 个）；
真发请求抽样 100 个里 **35% 纯 JSONPath 就能取到书名** ⇒ 外推约 130 个源只差一块 JSON 能力，可用源 87 → 200+。
（989 个**真 JS 执行**源不做。）

**① 什么时候走 JSON 路径**：响应体 trim 后首字符是 `{` 或 `[`（或 `Content-Type` 含 `json`）⇒ 当 JSON 解析；
解析失败就按原 HTML 路径继续试。**判据只看响应体，不看规则写法**（规则带 `$.` 的源也可能返回 HTML）。

**② 支持的前缀**：`@JSon:` / `@json:` / `@Json:` / `@JSON:`（大小写不敏感，求值前剥掉）。

**③ 支持的 JSONPath 子集**（与 Python 复刻 `pure_engine.py` 逐条同源，两边语义必须一致）：

| 写法 | 语义 |
|---|---|
| `$` | 当前节点本身 |
| `.key` / `a.b.c` / 裸字段名 `name` | 取字段（**裸字段名＝相对当前节点的规则**，不是选择器） |
| `[n]` | 数组下标；`[*]` / `.*` | 展开数组/对象的全部值 |
| `$..key` | **递归下降**：任意层级的同名键全找出来 |
| `?(@.key)` / `$.*[?(@.key)]` | **近似语义**：递归找该键，**该键的值是对象/对象数组**就取出来当条目（legado 是真过滤；键的值是标量时取不到 —— 用例里钉住了这条） |
| `a&&b` / `a\|\|b` | 备选，**取第一个有结果的** |
| `##正则##替换` | 对取到的字符串做替换（复用现有 `applyClean`） |
| `{{路径}}` | **模板插值**：把 `{{$.x}}` 用当前节点求值结果替换（用于 `bookUrl:"/novel/{{$.id}}"`）—— **仅 JSON 路径支持** |

**④ 明确不支持（遇到按「取不到」算，不许假装可用）**：`@js:` / `<js>` 真逻辑（`function`、`java.ajax`、
`java.base64`、签名/解密）；JSONPath 的切片 `[1:3]`、函数 `length()/size()`、`@put:`、`$..*` 通配；HTML 规则里的 `{{ }}`。

**⑤ 取值的兜底语义**（四处必须一致：`name`/`author`/`bookUrl`/`coverUrl`/`intro`/`kind`/`lastChapter`、
`chapterList`/`chapterName`/`chapterUrl`、`ruleContent`）：
- 取到字符串 → 按原样（`bookUrl`/`chapterUrl` 走绝对地址与「从原文抠网址」的兜底，与 HTML 路径同规格）；
- 取到数字 → 转字符串；
- 取到对象 → 按 `title/name/bookName/bookname/novelname/novelName/originalName` 挑第一个非空字符串；
- 取到数组 → 取第一个元素再按上面递归；
- 列表规则（`bookList`/`chapterList`）取不到列表时 **退回 `[整个响应]`**（单对象响应也要能取字段）。

**⑥ 三处接线（缺一即「搜得到、读不了」）**：搜索（`SearchWorker.searchSourceTask` + 本线程兜底
`BookSourceService.search`）、目录（`loadToc`）、正文（`loadContent`）；求值器单独一个文件
`utils/JsonRuleEngine.ets`。检测侧 `SourcePage.checkOne` 走的就是 `search`，所以自动跟随；
**雷达复刻不许比 App 宽**：`pure_engine.py` 同轮改，`selftest.py` 补 JSON 用例后 `engine_watch.py --accept`。

**⑦ 归因与预筛**：`compat_level()` 从「见 `$.` 就判 js」改为——**有真 JS 特征**（`function(`/`java.ajax`/
`java.base64`/`<js>`）才判 `js`；只有 JSONPath/接口写法的判 `ok`（值得实测），雷达照常按额度轮检。

### G.3 雷达判定：两档口径（2026-10-15 用户拍板「先拆两档」）

**为什么**：原来一个「可用」把两件事混在一起——能**搜到书名**和能**读整本**。2026-10-15 实测（抽 80 个
JSON 接口源：能搜到书名 28%、能走完全链路 0 个）证明这两者差距极大，含糊报数会误导决策。

| 档位 | 字段 | 判据（全部满足） |
|---|---|---|
| **搜索可用** | `verdict == 'usable'` | ① 站点探针通（只有解析不了/超时/5xx 算死）；② 用检测关键词（`剑来/斗破苍穹/诡秘之主`）逐个试搜，**任一**搜到书名 |
| **可整本抓** | 另加 `deep_ok == True` | 在「搜索可用」之上：① 目录规则能配出章节；② 第一条章号不明显 >3（`head_ok`）；③ 前 3 章里至少一章正文 ≥200 字（去空白） |

其余态不变：`reachable`（站点能开但搜不到）/ `down`（站点不通）/ `js`（规则要真 JS，跑不了）。
**报告与清单必须两档分开写**：禁止再用「可用 N 个」这种含糊话；导出清单也分两份
（`纯阅可用书源_<日期>.json` ＝ 搜索可用新增；`纯阅可整本抓_<日期>.json` ＝ 其中的可整本抓）。
标注沿用：`★` = 可整本抓 / `·` = 只能搜到 / `⚠` = 能抓正文但目录不从第 1 章开始。

### G.4 HTML 路径取值顺序（2026-10-15 修，别改回去）

**规则**：`##正则##替换` 必须在**补绝对地址之前**执行。取属性的唯一出口是
`RuleEngine.finalizeValue`（App）/ `pure_engine._finalize_value`（复刻）：**先套 `##正则##`，再给 `href/src`
补绝对地址**；`valueOf`/`attrOfTag` 只返回**原始属性值**，自己不做补全。

**为什么**：源的地址规则常写成 `a@href##^##https://www.shoujixs.net`（正则 `^` 替换成域名前缀；池子里
**100 个源**这么写）。旧顺序（先补绝对地址、再替换）会让替换作用在**已经带域名**的串上 ⇒ 主机名拼两次
（实测「手机小说」bookUrl = `https://www.shoujixs.nethttps://www.shoujixs.net/shoujixs_228918/`）⇒ 目录页取不到
⇒ 被误判成「不能整本抓」。同理 `href##/path/` 这类去前缀规则，旧顺序会得到缺斜杠的坏地址。

**副作用与语义边界**（用例里钉住了）：若源里的 href **本来就是绝对地址**，`##^##域名` 仍会拼两次 ——
这是 legado 同款语义（`##` 作用在原始值上，规则作者默认 href 是相对路径），**不是引擎 bug**。

**回归面**：改的是所有 `href/src` 取值 ⇒ HTML 引擎已纳入离线门禁
（`tools/jsonrule_selftest/test_html.ts` 跑生产 `RuleEngine.ets`+`HtmlUtil.ets`），并与复刻用同一份
`cases_html.json` 对拍（`check_python.py`）。

### G.5 书架条目的生命周期：**探到内容才入库**（2026-10-15 用户真机报，别改回去）

**现象（用户原话）**：搜书结果里**连续点几个源、都没成功抓取** → 书架上出现**多本同名 0B 书**（卡片显示「抓取中 · 0 章」）。

**根因**：`SourcePage.addToShelf()` 走的是「**开抓即入库**」——在 `BookSourceService.download()` **之前**就 `db.addBook()` 建条目 + 用 `makeBookPath()`（带时间戳）生成新路径。而 `download()` 的早失败分支里：

- `chapters.length === 0` ⇒ 抛「没有解析到任何章节…」，**文件从未创建**；
- 抓取循环里兜底只清了两种错误的其中一种（`err.message.indexOf('抓不到正文') >= 0` 才 `deleteBook + unlink`），**其余错误（目录 0 章 / 网络异常）只弹 toast** ⇒ 条目永久留在书架 = 0B + 「抓取中 · 0 章」。

**为什么会「多本」**：条目留下但文件路径不存在 ⇒ 下次点同名结果时 `findBookByTitle` 能查到这本，但 `fileIo.access(old.path)` 为假 ⇒ 判定「不在书架」⇒ 走 else **又插一行新路径**。点几个源就插几行，全是同名 0B。

**口径（铁律）**：

1. **先探后入库**：`download()` 先探（`loadToc` 出目录 **≥1 章** 且 首章 `cleanBody` **≥20 字**）——**探通了才回调 `.onReady()` 让调用方建条目**。探通之前的任何失败 ⇒ **零 DB 写入、零文件残留**。
2. **同名只一行**：同名（+作者）已有行，即使 `path` 不存在/文件 0 字节，也**复用该行并改写 path**，绝不 `insert` 第二行。
3. **早失败不留痕**：不得留 0B 文件或空条目；原「抓不到正文」那支的 `deleteBook + unlink` 保留（中途失败仍要清）。
4. **死条目自清**：启动时扫掉「`dlState=1` **且** `size=0` **且** 该 `path` 文件不存在」的行 —— 这类必然是残留（正常在抓的条目，文件在建条目之前就已存在且 ≥ 头部字节）。

**保留的用户体验**：「抓一半被杀掉/退出，书架照样看到这本书和「抓取中 · N 章」，再点同名结果接着抓」这条**不变** —— 因为探测只有 1~2 个请求，探测完立刻入库，后面长耗时的抓取阶段仍然「边抓边可见」。

## H. 官方 API 事实（2026-10-14 逐条核验，改相关代码前先看）

> 全部取自官方原文（OpenHarmony `docs` 仓 raw md / 华为开发者联盟页面），逐条 grep 命中，**不凭记忆**。
> H.1~H.4 是既有实现的依据补强与新坑；**H.5 是后台长时播放**（代码已实施 + 真机被清理后的加固与取证）。

### H.1 文件读取 API（服务待办 9「按章窗口读」）

| 事实 | 对本工程的意义 |
|---|---|
| `fs` 文本接口（`readText`/`readTextSync`/`readLines`）的 `encoding` **仅支持 'utf-8'**；`readLines` 读非 utf-8 抛 **13900037** | GBK/GB18030 书只能「按字节读 + 自己解码」——与 03-B 现有做法一致，此条是它的官方依据 |
| `fs` **没有 mmap**（官方 API 参考全文无该符号） | 大文件随机访问只有下面这条正路 |
| 随机/按章读：`createRandomAccessFile()` + `seek()`；或 `lseek(fd, off, WhenceType.SEEK_SET)` + `read(fd, buffer, {length})` | 待办 9 实现「当前章 ±3 章窗口从磁盘读」用这个 |
| ⚠️ **`ReadOptions.offset` 是「基于当前 filePointer 的相对偏移」，不是绝对偏移** | **新坑**：长跳转必须先 `lseek(SEEK_SET)`，否则静默跳错位置 |
| 跨块多字节截断：`decodeToString(u8, {stream:true})` 会把末尾不完整字节序列留在解码器内部缓存 | 03-B 已在用；03-B 记的「设备不认 `{stream:true}`」兜底分支**仍要保留** |

### H.2 编码探测（补 03-B「编码嗅探」的覆盖面）

- `util.TextDecoder.create(enc, {fatal:true})`：**非法序列会抛错**，正好当探测器用。推荐顺序：`utf-8` → `gb18030`（向下覆盖 gbk/gb2312）→ `big5`；BOM 优先（`EF BB BF` / `FF FE` / `FE FF`）。
- 官方编码白名单（可直接用）：`gbk`、`gb18030`、`gb2312`、`big5`、`shift_jis`、`euc-jp`、`euc-kr`、`utf-8`、`utf-16le/be`、`iso-8859-*`、`windows-125x`。
- 官方**没有**编码自动探测接口 ⇒ 探测必须自研（本工程已有，此条用于核对覆盖面）。

### H.3 列表 / 目录懒加载（目录几千章场景）

- `LazyForEach` 的硬约束是 **key 唯一且一致**；官方明确**禁止在 keyGenerator 里用 `stringify`**（大数据场景性能杀手）。
- `List`/`Grid` 的 `cachedCount` **默认只缓存 1 条**（不是「一屏一半」）；屏幕外预加载数量靠它调。
- 自定义子组件要加 `@Reusable` 才进复用池（目录项可考虑）。
- 可变高度的列表项**不影响懒加载**，只影响 `scrollToIndex` 定位精度 —— 这正是 03-C「像素滚动 + 自校准」存在的理由。
- 位置来源改造可用：`onScrollVisibleContentChange`、`getVisibleListContentInfo(x,y)`、`maintainVisibleContentPosition(true)`（**本工程当前均未使用**，属全新接入）。

### H.4 听书 TTS（Core Speech Kit）

- 引擎：`@kit.CoreSpeechKit` 的 `textToSpeech`；`createEngine({language, person, online, extraParams})` → `setListener(SpeakListener)` → `speak(text, {requestId, extraParams})`。
- 回调：`onStart` / **`onComplete`** / `onStop` / `onData(audio)` / `onError`；另有 `stop()` / `shutdown()` / `listVoices()`。
- ⚠️ **`requestId` 在同一引擎实例内只能用一次** ⇒ 逐段朗读必须每段生成新 id（否则串句乱播）。
- ⚠️ 单次 `speak` 文本长度有上限（社区口径约 1 万字符量级，**未在官方原文核实，需实测**）⇒ 长段必须切分投喂。
- `online` 决定在线/离线引擎 ⇒ **离线可用性未核实**，直接决定「飞行模式能否听书」。
- 同步口径：**以句/段为原子单位、`onComplete` 是唯一推进信号**；不要用定时器估算进度。
- **进度相关**：TTS 自动推进期间必须允许落库（A-4 的 G1 例外），否则听书进度丢失。

### H.5 后台长时播放（代码已实施；真机仍被清理 → 2026-10-15 加固）

**四件套 1.0.1 已全部落地**（别再说「未实施」）：`module.json5` 声明 `ohos.permission.KEEP_BACKGROUND_RUNNING` + `backgroundModes:["audioPlayback"]`；`Reader.startBgTask()` → `backgroundTaskManager.startBackgroundRunning(ctx, BackgroundMode.AUDIO_PLAYBACK, wantAgent)`（失败 1s 重试一次，仍失败 → `ttsBgBlocked` + 面板提示）；`continuousTaskCancel/Suspend` 监听（被停时如实置停）；`initMediaSession()` 建 `AVSession`（metadata=书名+章节名、playbackState、play/pause/stop/next/prev）；`stopSpeech → stopBgTask → stopBackgroundRunning`。用 `@kit.BackgroundTasksKit`。

**官方事实（2026-10-15 逐条核到，改这块前先看）**
- 「应用申请 AUDIO_PLAYBACK 类型长时任务，**退至后台时，如果设备没有有效音频播放，应用可能被系统冻结**」——「有效音频播放」是系统侧校验，不是只看有没有申请到任务。
- 「若音频在后台播放时被**打断**，系统会**自行检测并停止长时任务**，音频重启播放时**需要再次申请**长时任务」⇒ 被打断后恢复播放必须重申请，不能假设任务还在。
- 「后台播放音频的应用，在**停止长时任务的同时，需要暂停或停止音频流**，否则应用会被系统强制终止」⇒ 停播必须两者一起停（现在是 `stopSpeech` 里 `speaker.pause()` + `stopBgTask`，符合）。
- 取消原因码（`ContinuousTaskCancelReason` / API 26 `ContinuousTaskDetailedCancelReason`）：`3` 用户划掉通知、`4` 数据传输速率低、`5` **申请了 AUDIO_PLAYBACK 但未接入 AVSession**、`6` **申请了 AUDIO_PLAYBACK 但音频没在播放**、`11` 类型与实际业务不符（用错类型）。
- API 20 起：AUDIO_PLAYBACK 不接 AVSession → 由后台任务模块发通知；**接了 AVSession → 通知由 AVSession 发**（本工程属后者，所以「通知被关」= 长时任务通知发不出，等于没通知）。TTS 侧另有官方口径：`createEngine` 的 `extraParams.isBackStage=true` 才允许后台播报（本工程已设）。

**2026-10-15 真机实测失败（用户原话：「后台和锁屏还是会退出听书或被系统清理」）** ⇒ 本轮加固（都在 `Reader.ets`）：
1. **不再一被系统取消就自行停播**：`onBgTaskStopped()` 改为「先自动重申请（最多 3 次，间隔 1.2s/4s/12s），期间保持朗读」，只有三次都失败才 `stopSpeech` + 提示（旧行为是取消即停播——用户看到的「听书自己退出」很可能是这条）。
2. **被打断后自动补申请**：每段开始（`onSpeechSeg`）若 `ttsPlaying && !bgRunning` 且距上次申请 >5s → 重新 `startBgTask()`（对应官方「重启播放要再次申请」）。
3. **媒体会话心跳**：播放中每 5s `setAVPlaybackState(PLAY, position)`，保证系统侧一直看得到「在播放」。
4. **通知开关检查**：`notificationManager.isNotificationEnabled()` 为 false 时在听书面板给红字提示（通知没了 = 长时任务没通知 = 会被取消/冻结）。
5. **面板自检行**（用户真机取证的唯一手段）：听书面板显示 `后台保活：OK hh:mm / retry=N / cancel r=码 / suspend r=码 / fail 码`——真机再出问题，**截图这一行**就能定位是「没申请到」「被取消（哪种原因）」「被挂起」还是「通知被关」。
6. 回前台自检：`onForeground` 打 `appFgTick`，阅读页发现「在朗读但任务没了」→ 补申请。

**若自检行显示 `cancel r=6`（音频没在播放）**：根因就是「TTS 的音频流不在本应用名下，系统认为设备没有有效音频播放」→ 硬解只有一条：`speak` 的 `extraParams.playType=0`（官方口径：**0=只返回音频流、1=播放**）拿 `onData` 的 PCM（16 kHz/16 bit/声道随 `StartResponse`）→ 本进程用 `audio.AudioRenderer` 自己播（usage `STREAM_USAGE_MUSIC`、content `CONTENT_TYPE_SPEECH`），跟着把「段推进」改成按本进程播放进度推进。这是**下一步的备选方案**，不要在没看到 r=6 之前动它（会牵动听书高亮/跟随那一整套）。

**真机验收判据**：① 开始朗读后面板自检行 `OK`；② 切后台/息屏 5 分钟，回来时**朗读还在推进**（段号前进）、自检行没有 `cancel`/`suspend`；③ 日志 `hilog -x -T reader` 里没有 `continuousTaskCancel`/`continuousTaskSuspend`（有的话看 reason 码）；④ 锁屏播控中心有媒体卡、能控播。

❗**判据前提**：先在手机「设置 → 通知 → 纯阅」把通知打开。本机模拟器实测 `notifications enabled=false`（应用通知默认是关的）——通知被关时长时任务的通知发不出去，后台必然被系统停/冻结，先修这个再看别的。面板上的红字提示就是这条。

### H.5.1 本进程自播（2026-10-15 第二轮真机失败后的定案）

**现象（用户真机：两次「2 分多钟听不到」+ 切「性能模式」再试仍 2 分钟停）**：开听书 → 锁屏 → 约 2 分多钟止声；App 进程**没被杀**、回前台界面照旧、再点继续还能听。面板自检只留下 `reacquire-fail r=-1`（旧版单行显示，前面的 `cancel r=?` 被覆盖）⇒ 已改成**保留最近 3 次事件**（新包才看得到完整链）。

**判据链**：长时任务**申请成功**（`OK`）→ 系统在**固定窗口（≈2 分钟）**后判「应用未执行相应业务」→ **`continuousTaskSuspend` 把任务标记为暂停**（注册了暂停监听的版本，首次检测失败**不直接取消**，而是暂停）→ 「暂停态退后台会被挂起、回前台自动激活」→ 本进程 JS 停摆 → 系统 TTS 把手上那段念完就自然止声。省电/性能模式**都是 2 分钟** ⇒ 与省电模式无关，是**业务一致性校验**。

**根因**：本工程播报走 `eng.speak()` —— **音频流在系统 TTS 进程名下，本应用名下没有音频流**。官方口径：`continuous-task.md`「应用申请 AUDIO_PLAYBACK 类型长时任务，退至后台时，**如果设备没有有效音频播放，应用可能被系统冻结**」；暂停原因码 `5` = 未接入 AVSession、`6` = **未播放音视频**（`ContinuousTaskSuspendReason`，API 20+）。

**硬解（已实施，`utils/BookSpeaker.ets`）**：音频改由**本应用自己渲染播放** ——
1. `speak` 的 `extraParams` 加 `'playType': 0`（0=**只返回音频流**，1=播放）+ `'audioType': 'pcm'`；
2. `SpeakListener.onData(requestId, audio: ArrayBuffer, response)` 收 PCM（官方：**16 kHz / 16 bit**，声道随 `StartResponse.audioChannel`；`SynthesisResponse.sequence` 用于排序——**IPC 可能乱序**）；
3. `onStart` 里按 `StartResponse` 建 `audio.AudioRenderer`（`SAMPLE_FORMAT_S16LE` + `ENCODING_TYPE_RAW`；`usage: STREAM_USAGE_AUDIOBOOK`、`content: CONTENT_TYPE_SPEECH`）→ `write()` 推送自播 ⇒ **系统看得到本应用的音频流**；
4. **段推进改为按本段音频真实时长**（`字节数 ÷ (采样率 × 声道 × 2)`）＋ 120 ms 容差：不再依赖引擎「播报结束」事件（`playType=0` 时合成结束就回调，不能拿来当播完）；高亮跟随用**同一时钟** ⇒ 声音与高亮天然对齐；
5. 音量走 `renderer.setVolume()`（引擎不再负责播放这件事）；
6. **回落开关**：`selfPlay` 建渲染器失败、或 `onData` 迟迟不来（引擎不支持只取流）→ 自动退回 `playType=1`（旧行为）并打 `selfplay fallback` 日志 ⇒ 这块改坏也**不会把听书弄哑**。

**⚠️ 两个上报值都不可信（本机模拟器实测）**：`StartResponse.sampleRate` 报过 **48000**（按「字节数 ÷ 字数」反推其实是 16000）、`audioChannel` 报过 **1 和 3**（都不是声道数）。所以：采样率**一律按官方文档值 16000**；声道数用「字/秒必须落在 2~9 之间」**反推标定**（`calibrateSeg()`，进程内一次，首选 1 声道）—— 标定错方向不同：取小 = 声音变调变慢，取大 = 句子被拦腰截断，所以宁可单声道。

**模拟器实测（2026-10-15 14:16，hap `ca9134930b9a224110b9591fe0c2f5cf`）**：`selfplay calib ch=1 (chars=9 bytes=59066)` → `selfplay on rate=16000 ch=1` → `synth-done bytes=59066 dur=1846ms` → `seg done played=1786 dur=1846 req=pure_1`，实测语速 **4.0~4.2 字/秒**（改动前那套「260ms/字」估算在同一台机器上给 12 cps 的假值）；全程无 `probe`/`fallback`；系统侧 `AudioBackgroundManager [IsAllowedPlayback] … hasSession: 1, hasBackgroundTask: 1`。

**✅ 真机结论（2026-10-15）**：装上自播版后**锁屏连续 26 分钟播放正常**（同机同操作在自播之前**每次约 2 分钟必停**，省电/性能模式都一样）⇒ 「音频播放主体 ≠ 长时任务申请主体」就是那个 2 分钟定点的病根，本进程自播是有效解。⚠️ 别再退回 `eng.speak()` 直接播放的旧路径。

**验收判据**：① 模拟器：日志出现 `selfplay on` / `pcm N bytes` / 段按真实时长推进、高亮仍居中；② 真机：锁屏 **30 分钟**段号单调推进（无缺号、相邻 ≤ 段时长+2s）、面板自检无 `cancel`/`suspend`、锁屏播控中心有纯阅媒体卡且能暂停/继续。

### I.6 TTS 音色：引擎语言必须跟音色 + 不可用音色置灰（2026-10-15 真机 bug）

- **现象**（用户 nova14 Pro / HarmonyOS 6.1.0）：听书面板选「Laura · 英文女声」→ 点「开始朗读」→ 提示「朗读启动失败：%s」。
- **根因两条**：① `ensureEngine()` 把引擎语言**硬编码 `zh-CN`**，而 Laura 是 **person 8＝英文音色** —— 拿 zh-CN 建引擎必然失败；② 系统会弹**「是否下载以下语言包？」**，用户点「取消」时 `downloadVoice` **照样返回成功**（真机日志 `HiAI_TtsDownloadCallback: errorCode: 5, message: The user does not agree to download.`），旧代码却已经把该音色设成「当前音色」→ 播放时才炸。旧代码还会误报「音色已就绪」。
- **修法（已落地）**：① `BookSpeaker.langOf(person)`（person 8 → `en-US`，其余 `zh-CN`），`createEngine.language` 与 `speak.extraParams.languageContext` 都用它；② `Reader.voiceUsable()` 统一判定「可用」＝已安装 且（英文音色时正文必须不是中文）；**不可用的一律置灰 + 划线**，`pickVoice()` 里再加一道硬闸（别的入口也拦得住）；③ 点不可用音色 = **只下载不切换**；④ 下载中置 `voiceDlBusy`，**禁止开始朗读**（下载占着 TTS 引擎，此时建引擎会**静默卡住**：日志一条没有、界面一直停在「开始朗读」——本机模拟器实测）；⑤ 下载结束后**回查真实安装状态**再决定说「已就绪」还是「暂不可用」。
- ❗**语言判定必须看「当前章正文」，不能看 TTS 分段**（2026-10-15 用户报：「打开英文文章听书前选不了英文女声，用别的音色听一遍再停止反而又能选」）：分段（`speaker.exportSegs()`）是**听过书之后**才存在的东西 —— 没听过时取样为空，旧代码保守判成「中文」，英文文章里英文女声被错误置灰；听过一遍后分段有了、判定改口，就又能选了（正是用户看到的现象）。现在 `contentLooksChinese()` **优先看 `curText`**（打开书就有，与听没听过无关），分段只作兜底。
- **判定阈值**：`looksChineseText()` = **汉字数 × 3 ≥ 拉丁字母数** 才算中文（中文正文常夹英文单词/网址/人名，采用「谁多算谁」会把中文书误判成英文书 → 给中文书放出英文音色，正是用户点名不要的）。判定顺序也调整过：`voiceUsable()` **先判语言、再判是否已下载**（先判下载会在未下载时短路掉语言判定，让结论随无关状态漂移）。
- 文案：`rdr_126`（正在下载音色：%s）/ `rdr_127`（该音色暂不可用…）/ `rdr_128`（音色正在下载，稍等一下再开始朗读），11 套同步。

### I.7 深色模式下输入框看不见（固定白底 + 主题默认字色）

- **现象**（用户 Mate 70 / HarmonyOS 7）：首页 → 新建文件夹 → 切系统深色后**输入框内容看不见**。
- **根因**：弹窗卡片是**固定白底**（`Color.White`），而 `TextInput`/`TextArea` 没写 `fontColor`/`placeholderColor` ⇒ 文字色**跟随系统深色主题变白** → 白底白字。App 里 `EntryAbility` 设的是 `COLOR_MODE_NOT_SET`（跟系统），首页根容器又是 `Color.White`，所以只有「跟主题的控件 + 固定浅底」这一组合会瞎。
- **修法**：所有输入框**显式上色**（`fontColor('#1A1A1A')` + `placeholderColor('#999999')` + `caretColor('#3A6EA5')` + `backgroundColor('#F5F5F5')`）：书架「新建文件夹」+ 书源页 4 处（公版搜索、网址导入、粘贴 JSON、搜书关键词）。**Text/Button 不用管**（Button 都自带底色），全项目扫过一遍只剩这些输入框。

### I.8 音色按书记录 + 语言守卫（2026-10-15 用户报，新增需求）

3. **语言守卫（关键）**：解析结果还要与**正文语言**比对 —— 不匹配 ⇒ **自动换成该语言默认音色**（中文→13、英文→8）并提示；默认音色没装 ⇒ 保持原音色（面板里本是置灰的），不硬切到装不了的音色。触发点放在**开始朗读前**（那时正文/样本必定有，判定可靠；刚打开书时样本可能为空，`contentLooksChinese()` 会保守判中文，不能作为唯一触发点）。

### H.6 真机 9800005「系统限制了后台播放」——长时任务一致性校验（2026-10-15 晚 修）

**现象**：真机（HarmonyOS 7 / Mate 70）听书面板红字「系统限制了后台播放，锁屏后可能中断」，
保活自检行连续 `fail 9800005`（18:28 / 18:29 / 18:29）。同一时刻**模拟器上完全正常**
（`startBackgroundRunning OK`），所以本地怎么测都复现不了。

**根因**：`9800005 = Continuous task verification failed` —— AUDIO_PLAYBACK 长时任务有
**运行态一致性校验**：系统在**申请那一刻**确认「该应用确实有有效音频在播放」。
旧代码把 `await this.startBgTask()` 放在 `speaker.play()` **之前**（音频还没起播）
⇒ 真机校验严格，直接打回；**模拟器不做这项校验，所以永远 OK**。
（官方文档：「若应用申请了长时任务，但未真正执行申请类型的长时任务…例如系统检测到应用
申请了 AUDIO_PLAYBACK，但实际未播放音乐，长时任务会被取消」；「退至后台时如果设备没有
有效音频播放，应用可能被系统冻结」。）

**改法**（`Reader.ets` + `BookSpeaker.ets`）：
1. `BookSpeaker.isAudioLive()`：最近 **3s 内**有 PCM 写进**本进程** AudioRenderer 才算「音频在播」
   （`pump()` 每次 `renderer.write()` 成功记 `lastWriteMs`）；另加 `isSelfPlaying()` 看是否走自播。
2. `startBgTask()` 改成**轮询申请循环**：音频没真在播就不申请；起播后按 300/500/800/1200/2000/3000→5000ms
   退避重试；拿到就停循环；起播后连续 20 次（约 40s）拿不到才置 `ttsBgBlocked` 提示用户。
3. 自检行加了 `sp:on/off`（是否自播）+ `audio:live/none`（本应用音频是否在播）——
   **真机截图一眼就能看出是不是回落给系统 TTS 播了**（回落时 sp:off + 校验必挂）。

**验收铁律（新增）**：`9800005` 这类**一致性校验**问题**模拟器验不出来**，
必须真机看自检行 `OK`；模拟器只能验「代码路径不报错」。改长时任务相关代码时，
先把自检行的 `sp/audio` 两段读出来。
