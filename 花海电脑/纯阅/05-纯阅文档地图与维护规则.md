# 纯阅 · 文档地图与维护规则

> 目的：**一份口径只写一处**，避免"两个会话同时改、同一句话两套说法"。本文是文档层的规定，改任何纯阅文档前先照它办。

## 一、文档地图（谁拥有什么）

| 文档 | 类型 | **所有者** | 口径地位 |
|---|---|---|---|
| `00-纯阅总纲` | 索引/定位/工作流 | 虾米 | 索引入口（**不写口径**，只写导航与关键事实） |
| `01-纯阅功能规格` | 规格 | 虾米 | **规格唯一来源**（软件"应该是什么样"） |
| `02-纯阅工程与架构` | 工程 | 虾米 | **工程事实唯一来源**（模块/表/sidecar 格式/构建签名/调试） |
| `03-纯阅关键约定与踩坑` | 约定/红线 | 虾米 | **红线与口径唯一来源**（位置锚、护栏、踩坑） |
| `04-纯阅待办与验收` | 待办/验收 | 虾米 | **待办与验收判据唯一来源** |
| `05-纯阅文档地图与维护规则` | 规则 | 虾米 | 本文（命名/frontmatter/冲突裁决/并发写入） |
| `docs/fix/**` | 专项修复细化 | **桌面会话（试用新版纯阅）** | 只写"怎么修"（根因/方案/任务卡/用例）；**不得**写规格、不得写验收判据 |
| `docs/optimize/**` | 优化方案 | 虾米 | 只写"建议与做法"；目标指标转正后进 `01`/`04` |
| `docs/design/**` | 设计方案 | 虾米 | 只写"怎么实现"；规格转正后进 `01` |
| `docs/review/**` | 复核结论 | 虾米 | 一次性结论；处置落地后状态改 🗄 已归档 |

## 二、口径唯一性（核心规则）

**一个口径只允许在它的"唯一来源"里写正文，其他地方只放链接。**

| 内容 | 唯一写在哪 | 别处怎么写 |
|---|---|---|
| 规格（该有什么行为） | `01` | 只写"见 01 §X" |
| 模块/表/sidecar/构建/调试 | `02` | 只写"见 02 §X" |
| 红线、位置锚、护栏（G1~G4）、踩坑 | `03` | 只写"见 03 §X" |
| 待办状态、验收判据 | `04` | 只写"见 04 §X"（**不许**在专项文档里另立判据表） |
| 目标指标（PSS/首屏/包体…） | `01`（规格级目标） | 专项文档只引用 |

⚠️ **反例（今天就犯过）**：`G1/G3` 在 `03`、`fix-plan`、`test-strategy`、`docs/review` 各写了一遍；`148MB→40MB` 在 6 份文档里出现。**允许的写法**：`03` 写正文，其他写"护栏口径见 03-A-4"。

## 三、冲突裁决顺序（照这个判，不用吵）

```
① 用户本次拍板（含群里的原话）
② 01 规格
③ 03 红线与口径
④ 04 待办与验收
⑤ 专项文档（docs/fix / optimize / design / review）
```

低优先级文档与高优先级冲突时：**改低优先级的**，并在 `04` 的改动记录里留一行。

## 四、并发写入规则（防两会话互踩）

- **一个文件同一时间只允许一个会话改**（文件所有权见 §一）。
- 桌面会话改代码 + `docs/fix/**`；虾米改 `01~05` + `docs/{review,optimize,design}`。
- 要改别人拥有的文件：**先在飞书群里说一句**，或在 `04` 里写一条"请 XX 改"。
- 两边都在改同一文件时：**先 pull（`git pull --rebase --autostash`）再改**；冲突不许硬推。
- 代码侧同规则：**`Reader.ets` 一次只一个会话改**（历史教训：两边互相覆盖）。

## 五、命名与 frontmatter 规范

**文件名**
- 顶层：`NN-名称.md`（`00`~`05`）；子目录：`YYYY-MM-DD-短名.md`（如 `2026-10-14-优化方案-性能体验视觉.md`）。
- **禁用全角括号 `（）` 与 `·`**（命令行/链接易踩坑）；用半角 `-` 分隔。
- 一个主题一份文档；被取代的文档不删，头部标 `状态: 🗄 已归档（被 …取代）`。

**frontmatter（统一这 6 个键）**
```yaml
title: 纯阅 · 中文名
项目: 纯阅（HuaweiReader）
类型: 规格 | 工程 | 约定 | 待办与验收 | 规则 | 专项修复 | 优化方案 | 设计方案 | 复核结论
所有者: 虾米（Hermes） | 桌面会话（试用新版纯阅）
更新: YYYY-MM-DD
状态: ✅ 生效 | ⚠️ 待验收 | ⬜ 未实施 | 🗄 已归档
```

**状态标记（正文内）**：`✅ 已实现并验收` / `⚠️ 已实现但验收未过` / `⬜ 未实现`；不要自造别的符号。

## 六、改完必跑的自检（6 条）

1. **wikilink 能对上**：`[[名字]]` 或带别名 `[[名字|显示名]]`；子目录用路径形式（如 `[[docs/design/2026-10-14-文本整理流水线|文本整理流水线]]`）。**示例要放进行内代码**（`` `[[…]]` ``），否则自检脚本会把它当死链；
2. **口径只出现一处**（§二）；
3. frontmatter 6 键齐全、文件名合规（§五）；
4. 路径统一正斜杠 `E:/HuaweiReader`；命令块标语言；UTF-8 无 BOM；
5. **改完 `git pull --rebase --autostash` 再 push**（vault 走 GitHub，需代理 `127.0.0.1:10808`）；
6. 改了规格/待办 → 在 `04` 的「改动记录」补一行（日期 / 改了什么 / 影响面 / 验收状态）。
