## 接口（关键发现：纯 HTTP SPA，可完全绕开浏览器）
- 端点：`POST http://mir.uuuyx.com/mir/game/do.php`，body 为 form-urlencoded，参数 `m`(模块) `a`(动作) + `md5`(登录令牌)。
- 登录：`m=account&a=login&username&password&server=1` → 拿 `md5` 与 `area` 列表（永久区=area 2）；再 `m=login&a=login&area=2&md5=...` → 返回新 md5。后续每次请求都带最新 md5。
- 返回 `b=1` 成功，其它值 + `t` 是错误文案；返回里的 `user` / `data` 是增量状态，需合并。
- 前端 JS 单文件（`/assets/main-*.js`，~800KB）内含全部接口定义，可 grep `{m:"模块",a:"动作"}` 反查。

### 天书规则（重要）
- **特效判定：物品行的 `slvl` 就是特效编号**（前端 `slvl>0 && 类别!=='宝石'` 才显示「特效」）。特效名表：**1麻痹 2复活 3护身 4隐身 5防麻痹 6防复活 7防护身 8防隐身**。
- 天书 itemid = **698**（`aclass=装备, bclass=天书`，全部天书都是这个 id，区分靠 `slvl`）。
- `slvl>0` → 上锁（`item.suo(id,1)`，已锁则跳过）；`slvl==0/无` → 喂祭坛 `jt.give(id=3)`。
- **必须在「一键熔炼」之前上锁/搬走**，否则会被 allsell 一起熔掉。
- 实测（2026-09-16）：3 本天书（1 本 `slvl=5` 防麻痹已锁 + 2 本无特效）→ 执行后只剩特效那本，2 本无特效已喂祭坛，背包 49→47。

实现：`daily.py` 的 `storage_maintenance(...)`（完整处理）+ **`after_stage(m, dry, path, tag)`**（哨兵入口）+ `tianshu_rule()` / `donate_gems()` / `smelt_bag()`。
- **挂载点（用户定：每次幻境/秘境后）**：`main()` 里 7 个调用点 —— 幻境(签到前) / 幻境(祭坛重置后) / 幻境(补领昨日后) / 秘境(签到前) / 幻境(签到后) / 秘境(签到后) / 押镖前。**不用定时 cron**。
- **两条路径**：有溢出或仓库全满 → 完整处理（⓪天书上锁/喂祭坛 ⓪.5 ①宝石供奉 ②600+存仓 ③一键熔炼低级装备 ④回收系统四样 ⑤取临时背包，循环到无变化）；否则若有天书/宝石/低级装备 → **轻量清理**（⓪①③）；都没有 → 只记一行。
- 触发条件（避免噪声）：`user.item102` 含「临时背包」**或** `no_room(pages)`（所有已开启页都 35/35）。只是某页满、其他页有空、又无溢出 → 只记一行（否则 page3 长期满，每次都刷一屏日志）。

### 「打到不能再打」的判定（关键）
- **`hj_num`/`mj_num` = 战败计数，满 200 就锁**——这才是「不能再打」：
  · 幻境：`你的战败次数过多,需要签到或其他方法重置幻境。`
  · 秘境：`当前等级无法继续挑战更高秘境。`（秘境上限 = 人物等级+100）/ `巅峰后才可以挑战。`
- 代码里用 **`is_exhausted(reason)`** 判定（只认这三种服务端文案）；**时间预算用尽 / 本段上限 / 网络错误 都不算用完**，此时绝不能重置（否则白浪费重置额度）。旧的 `is_bottleneck()` 过于宽松，已不再用于门控重置。
- `climb()` 里 **不能有提前停手的保护**：曾经的「胜利后层数未推进连 3 次就停」会违背“打到不能再打”，已改为只记日志继续打（每 50 次提一句）。
- 帮助原文（`m=user&a=help&id=34` 幻境 / `35` 秘境）：幻境「**请尽量每次都打到不能再打为止再重置**」「每天签到重置层数、也可以通过祭坛/幻境重置卷/红包重置层数」「有挑战失败次数限制」「每周六、日双倍幻境经验」；秘境「可挑战层数上限=人物等级+100」「建议佩戴防麻痹+防隐身护腕」。
- 实测（2026-09-16）：主号 `hj_num=200`、`mj_num=200` → 幻境返回「你的战败次数过多…」、秘境返回「当前等级无法继续挑战更高秘境。」，`is_exhausted` 均 True。

## 宝石规则（用户 + 游戏内《符文之语》文档）
**有特效的宝石 = 物品行里有 `g1` 字段**（前端渲染成「附加·<属性>」，`g1|g2` 即「属性id|数值」，`g2/10%` 为百分比）。
⚙️ 属性名表在字典的 **`shuxing`**（26 条：生命/法力/前攻击/攻击/…/魔防），前端用 `Z(id)` 查它——所以宝石的“特效”**不是** `slvl`（宝石的 `slvl` 是经验值、`g2` 是经验上限基准）。

| 操作 | 公式 | 实测 |
|---|---|---|
| 有特效（任意等级） | **存入仓库** | ✓ |
| 无特效一级 | **直接喂祭坛** `jt.give id=7`（不合成） | ✓ |
| 二级→三级 | 2×二级 + **4#** | ✓ 「合成成功，获得三级宝石×1」 |
| 三级→四级 | 2×三级 + **6#** | ✓ 级联自动往上合 |
| 四级→五级 | 2×四级 + **8#** | |
| 五级→五级 | 2×五级，**不要符文**（博特效） | |

- 符文 itemid：**1#=501 … 10#=510**（“对应的号数符文” = 2N# 对应 N 级）。
- ⚠️ **有特效的一级宝石不能喂祭坛**（先存仓库再喂无特效的）——旧 `donate_gems` 会把所有 543 都喂掉，已改成只喂 `g1==0` 的。
- 实现：`daily.py` 的 `gem_rule(m, bag, pages, dry, path)`；合成循环每轮重取背包（行 id 会变），缺符文就停。

## 仓库按类别整理（用户要求）
仓库只有 **3 页 ×35 = 105 格**，而装备就有 63 件 → 「一类一页」装不下，按部位分组（`STORE_CATEGORY` + `STORE_FALLBACK_PAGE`）：
- **页1 = 镶嵌类**（石头/符文/天书）; **页2 = 首饰**（戒指/项链/手镯/勋章/特戒/护腕）; **页3 = 防具武器+杂项**（头盔/衣服/武器/靴子/腰带/材料…）。
- 实现 `organize_store()`：仓库页间无直通接口 → 「`itemku type=2` 取出到背包 → `itemku type=1&ku=目标页` 放入」两步走，允许多轮（先腾空位再补位）；目标页满就跳过；**上锁的不动**。实测 79 件→移动 55 件后收敛，再跑移动 0 件（幂等）。
- **坑（重要）**：**可叠加道具（num>1）不能这么搬**——取出时会与背包里的同类堆叠**合并**、行 id 变化，第二步报「无此道具」，而且会把背包那堆一起带走。所以 `organize_store` **跳过 num>1 的道具**（实测 BOSS卷轴 30149 与背包 233 合并成 30382，东西没丢但位置错了）。

## 世界BOSS 刷新时间预测（沙巴克报名数 → 行会战时长）
实测规律（2026-09-13）：行会战是**两两配对打一轮（KOF）**，场次 = **C(N,2)** — 10 个行会恰好 45 场；18:01:37 开打、18:28:35 结束（27 分钟，每场 36 秒）。世界BOSS 在行会战结束后才重置。
实现：`mir_bot/wbpredict.py`（历史 `worldboss_history.json`）。
- 数据源：报名行会 `m=hh&a=loadsignlog&page=1` → `sbk.signlog`（**报名数**）；战役日志 `m=hh&a=loadpklog&type=1&page=1..` → `sbk.pklog`（每场对手 + 时间戳，用于反推开战/耗时）；`hh.sbk` 的 `sbk_date` = 结束（占领）时刻。
- 模型：重置≈开战时刻 + C(本周报名数,2) × 每场秒数 + 结束后延迟；两个参数（每场秒数、延迟）用实测滚动更新。
- 自修正闭环：追击守护进程检测到重置时调 `wbpredict.record_reset()` 写入实测 → 下周预测自动用新值；守护进程每 10 分钟刷新一次预测（报名数会陆续增加）。
- 命令：`python wbpredict.py --observe / --predict / --show / --record-reset "YYYY-MM-DD HH:MM:SS"`。
- 守护进程按预测调轮询密度：**预测窗口内 2 秒/次**，其余 10 秒/次，追击中 3 秒/次。

## 漏洞排查结论（2026-09-17 实测，别重复劳动）
用户问过「有没有漏洞可以利用」。**结论：服务端校验很规矩，没有「改个数字就白拿」的漏洞。** 排查脚本：`mir_bot/probe_bugs.py` / `probe_bugs2.py` / `probe_bugs3.py`（都用测试号 `hu_test_01` 1 区，不动主号）。
- 接口全集：前端 `/assets/main-*.js`（~800KB）里 grep `{m:"..",a:".."}` = **174 个**端点，含 `st.*`(师徒) `skill.*` `db.*`(宝箱/寻宝) `code.*`(激活码/推广提现) `sell.*`(寄售,需交易权限) `item.top*`(极品殿堂) 等。
- **层数参数是客户端传的，但服务端忽略它**：`hj.fight id=9999` 实测照样打出「幻境1层」（`fight.bname` 恒为当前层），`mj.fight id=9999` 直接报「巅峰后才可以挑战」。⇒ 不能跳层。
- **数量参数服务端自己夹**：`fight.bosssd num=999` → 「扫荡最大次数限制100」（前端也 clamp 到 999，服务端更严）；`num=-5` → 参数错误。`jt.give/back.sell/item.yong/dj.*` 传不存在/未持有的道具一律拒（「背包中无此道具」）。
- **次数/条件服务端校验**：`fight.boss`(次数不足)、`boss.fight`(世界BOSS次数)、`user.lvup`(经验不足)、`user.redbag`(红包<100万不能拆)、`code.code`(无此激活码)、`shop.holiday`(非节日)、`db.baoxiang`(需《宝箱钥匙》)。

## 坑
- **物品字典其实能拿**：`http://mir.uuuyx.com/data/data.txt`（379KB JSON: item/map/monster/skill/boss/task/title/city/achieve/fw/jue/shuxing/topitem）。**必须带浏览器 UA + `Referer: http://mir.uuuyx.com/mir.html?server=1`**，否则站点 WAF 返回 404 页面（早期结论“404 拿不到名字”是错的，已由 `mir_items.py` 修正）。
