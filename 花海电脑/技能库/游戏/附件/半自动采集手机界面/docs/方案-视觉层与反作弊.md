**■ 倩女幽魂手游自动化 —— 视觉层选型 + 反作弊分析（实测标定）**

实测日期 2026-09-18。所有数字来自 `scripts/bench_discriminators*.py` 在本机真实运行，
合成界面分辨率 = 游戏真实横屏分辨率 **1600x720**。

---

**▍ 第一部分：运行时界面判别器选型（0 token 方案）**

**· 1.1 被证伪的方案**

| 方案 | 实测结果 | 为什么不能用 |
|---|---|---|
| **全屏 aHash / dHash**（16x16） | 类内 0.00~0.33，**类间（背包）距离仅 3** | 游戏界面普遍深色底+少量 UI，全图均值阈值化后哈希几乎全同，任何两屏都"形似"。**彻底不可用** |
| **多点比色（6屏共享固定网格）** | 类内最差 0.67 / 类间最好 0.67 → 重叠 | 采样点大半落在共享的深色底上，无区分度 |
| **多点比色（按跨屏方差自动选点）** | 类内最差 0.08 | 方差最大的点全落在**标题文字的抗锯齿边缘**，4px 偏移即全变色 |
| **cv2 模板匹配 @1/4 降采样** | 类内 0.906 / 类间 0.797，裕度仅 +0.110 | 降采样抹掉细节，不同按钮形状趋同 → 裕度不足 |
| **OCR ROI 无置信度阈值** | `背包` 被误读成 `背包電`，置信 **0.722** | 必须设置信度阈值（见 1.2-C） |

**· 1.2 可用方案（最终选型）**

**·· A. 多点比色（最快，~2ms；但有两个硬条件）**
- **硬条件①：采样点必须落在纯色块深处。**
  用 **11x11 窗口**内跨屏最大标准差 **< 1.0** 作为筛选约束（即离任何边缘 ≥5px）。
  - 3x3 约束 → 类内最差 **0.17** ❌；11x11 约束 → 类内最差 **1.00** ✅
- **硬条件②：每通道容差 —— ⚠️ 原写「≥35」已作废，待真机重标。**
  原 35 是拿**合成扰动** `bright ×1.10` 标出来的，但**实测屏幕亮度对截图像素毫无影响**
  （见下方「亮度实验」），该扰动不真实 → 容差偏松。
  参照系：大漠 `CmpColor` 相似度 **0.9 ≈ 每通道容差 25**。
  真正要处理的是**弹窗变暗遮罩 / 半透明 UI / 场景光照**这类**结构性**扰动 ——
  靠**选点避开**，而不是放宽容差（放宽容差会让「配色相近的界面互相混淆」，实测已踩过）。

  **亮度实验（2026-09-18 真机实测，`scripts/test_brightness.py`）**：`screencap` 抓的是
  SurfaceFlinger 合成后的**帧缓冲内容**，亮度施加在**背光/面板层（帧缓冲之后）**，属物理层面。
  ```
  亮度 37(原始) vs 5(最暗)     平均差 0.106  最大差 17  变化>10 的像素 0.0004%  96.11% 完全相同
  亮度 37(原始) vs 255(最亮)   平均差 0.093  最大差 17  变化>10 的像素 0.0005%  96.44% 完全相同
  亮度 5(最暗)  vs 255(最亮)   平均差 0.104  最大差 17  变化>10 的像素 0.0006%  96.17% 完全相同
  ```
  **判定依据**：亮度差 32 级（37→5）与差 250 级（5→255）造成的差异**几乎相同**
  （0.0004% vs 0.0006%）；若亮度有影响，后者应显著更大。→ 那 0.0006% 来自两次截图
  间隔（2.5s）里**游戏画面自身在动**。12 个采样点在**容差 0（逐位全同）下仍 12/12 命中**。

  **真正的扰动源与对策**：
  | 扰动源 | 影响截图像素 | 对策 |
  |---|---|---|
  | 屏幕亮度 / 自动亮度 | ❌ 不影响（已实测） | 无需处理 |
  | 护眼模式 / 色温 | ⚠️ 看厂商实现 | 需实机验 |
  | **弹窗全局变暗遮罩** | ✅ 影响大，且会压暗 HUD | 选点避开被压暗区域；或按「有/无弹窗」分状态 |
  | **半透明 UI 透出场景** | ✅ 影响大 | 选点落在不透明元素上 |
  | 场景光照 / 昼夜 / 天气 | ⚠️ **只影响半透明 UI / 透出场景区域；不透明 UI 面板不受影响** | 采样点落在不透明 UI 上，避开 HUD 半透明底 |
  | **UI 开合动画进行中** | ✅ 影响 | 时序问题：等动画结束再截图 |
  | 游戏内画质档位 | ✅ 影响 | 固定档位后重标 |

  → **改进选点算法（取代"合成扰动"法）**：**跨状态重复采样选点** —— 同一界面在多种真实状态
  （有/无弹窗、不同地图光照、不同时段）下各截 N 张，对每像素取
  [跨状态方差小] × [跨界面差异大] 最大的点（且满足平坦约束）。这样选出的点天然免疫上表扰动。
- 用时：单次签名提取 **~2ms**（numpy 索引，无需 cv2）。
- **结论：可用，且是最便宜的一级否决。但采样点必须靠"自动筛选 + 平坦约束"选出，不能手拍。**

**·· B. cv2 模板匹配 `TM_CCOEFF_NORMED`（最稳，能同时给出坐标）**

| 降采样 | 耗时 | 类内最差 | 类间最好 | 裕度 |
|---|---|---|---|---|
| **1/1 全分辨率** | **24.0ms** | **0.934** | **0.498** | **+0.436** ✅ 首选 |
| 1/2 | 11.2ms | 0.917 | 0.615 | +0.302 ✅ |
| 1/4 | 5.0ms | 0.906 | 0.797 | +0.110 ⚠ |

- 全屏 1600x720 搜索 120x60 模板 = 24ms；**推荐阈值 0.70~0.85**（裕度居中）。
- 纯 numpy 手写同算法需 **1100ms** → **必须用 cv2**（已装 opencv-python 5.0.0.93）。
- 模板匹配是**唯一能同时输出按钮坐标**的方案 → 点击定位必用。

**·· C. OCR ROI 模式（语义确认 / 兜底，~9ms）**
- **必须 `use_det=False, use_cls=False, use_rec=True`**：从 **1001ms → 9ms**（110 倍）。
  带检测器时 ~1.0s 完全不能用于运行时。
- 返回结构：`[['日常任务', 0.993]]` → 取 `res[0][0]`（不是 `r[1]`，那是置信度）。
- 实测：`日常任务` 0.993 ✅ / `倩女幽魂` 0.999 ✅ / `背包`→`背包電` **0.722** ❌
- **必须设置信度阈值，建议 ≥0.9，低于则丢弃并降级到模板匹配。**

**· 1.3 推荐运行时级联（总成本 2~35ms / 次，0 token）**

```
① 比色指纹 (2ms)  ── 命中 ──▶ 返回界面 ID
      │ 未命中
② cv2 模板匹配 (24ms) ── 峰值≥0.8 ──▶ 返回界面 ID + 按钮坐标
      │ 未命中
③ OCR ROI (9ms) ── 置信≥0.9 ──▶ 返回界面 ID（语义）
      │ 未命中
④ 兜底：存截图 + 停手报警（可选开 LLM 兜底，默认关）
```

**▍ 第二部分：反作弊 / 防检测分析**

**· 2.1 注入通道对比（核心表）**

| 通道 | 事件特征 | 主要检测点 | 隐蔽性 | 本机可用性 |
|---|---|---|---|---|
| **PC adb `input`** | `deviceId=0`、`source=0`(SOURCE_UNKNOWN)、`pressure=1.0` 固定、`size=0`、无历史采样点 | ① `MotionEvent.getDeviceId()` 异常 ② `getSource()` 非 `SOURCE_TOUCHSCREEN` ③ `Settings.Global.ADB_ENABLED` 检测 ④ 无对应 `InputDevice` 实体 | **最低** | ✅ 零改装即可用 |
| **手机端无障碍 `dispatchGesture`**（按键精灵/AutoX/Auto.js 走这条） | `source=SOURCE_TOUCHSCREEN`，但 `deviceId` 仍为 **-1** | ① `AccessibilityManager.getEnabledAccessibilityServiceList()` **直接抓包名** ② 已知框架包名黑名单（`com.cyjh.mobileanjian` / `org.autojs` / `com.touchsprite`） | 中 | 需在手机装框架 |
| **root + uinput 注入** | 注册成**真实输入设备**，事件带正常 deviceId / pressure / size / 历史点 | ① `InputDevice.getDeviceIds()` 出现可疑设备名 ② `/proc/bus/input/devices` 可读 ③ root 检测（su / Magisk） | **高** | 需 root |
| **硬件 HID（OTG 模拟触摸屏）** | 系统视为**真外接触摸设备**，游戏无法与真人触摸区分 | 只剩**行为分析**（轨迹/节奏/在线时段） | **最高** | 需额外硬件（Arduino/ESP32 + HDMI 采集卡做视觉） |

**· 2.2 独立于注入通道的检测面**

1. **已安装应用扫描** —— 游戏遍历包名找按键精灵/触动/AutoX/GG修改器。
   → **这是"自制脚本优于知名框架"的核心理由。**
2. **root / 越狱检测**、**Frida / Xposed 检测**。
3. **模拟器检测**：`ro.kernel.qemu`、传感器数量、CPU 特征等。
4. **VMOS / 云手机检测** —— ⚠ **用户手机已装 `com.vmos.pro`（VMOS Pro 2.9.6），
   部分游戏会直接标记安装过虚拟机的设备。**
5. **`FLAG_SECURE` 截屏拦截** —— 某些界面禁止截屏时，adb `screencap` 得到**全黑图**。
   这是硬限制，需在真机上验证倩女幽魂是否对特定界面设了该 flag。
6. **行为风控（网易易盾这类，权重最大）** —— 点击分布、轨迹曲率、反应时延分布、
   在线时段/时长模式、操作序列重复度、多账号同 IP/设备指纹。

**· 2.3 关键判断**

- 网易这类厂商，**行为风控权重 > 注入通道检测**。通道选得再好，
  恒定节奏/固定坐标/24 小时在线的行为一样会被盯上。
- 所以优先级应是：**行为拟人（已有实现） > 通道隐蔽性 > 框架选择**。
- 拟人层已实现：零距离 swipe 造真实 DOWN→UP、±5~12px 坐标抖动、
  对数正态间隔（偶发 1.2~3.5s 走神停顿）、滑动拆 4 段带弧度变速。

**· 2.4 三种架构取舍（待用户拍板）**

| 架构 | ADB 需常开 | 输入特征 | 算力 | 改装成本 | 备注 |
|---|---|---|---|---|---|
| **A. 全程 PC adb 驱动** | 是 ⚠️ | adb input（最低隐蔽） | 强（PC） | 0 | 最快能跑起来；检测点③长期暴露 |
| **B. PC 只做视觉 + 手机端注入** | 建图时开，运行可关 | 手机端无障碍/root | PC 视觉 + 手机注入 | 中（要装/写手机端） | 折中 |
| **C. 全手机端自制 APK** | **否**（可关开发者选项） | 手机端，且非知名框架 | 弱（手机） | 高（写 Android 代码） | 隐蔽性最好；本机 DLP 限制只影响 C++，Java/Kotlin 可编 |
