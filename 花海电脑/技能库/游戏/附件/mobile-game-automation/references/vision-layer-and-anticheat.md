# 运行时界面判别器 + 反作弊（2026-09-18 实测标定）

合成界面分辨率 = 游戏真实横屏 **1600x720**。完整版与脚本在 `E:/AiDemos/QnyhAuto/`
（`docs/方案-视觉层与反作弊.md`、`scripts/bench_discriminators*.py`）。

## 一、判别器选型（运行时 0 token）

### 被证伪
| 方案 | 实测 | 原因 |
|---|---|---|
| 全屏 aHash/dHash 16x16 | 类内 0.00~0.33、**类间(背包)距离仅 3** | 游戏界面深色底+少量UI，全图均值阈值化后哈希几乎全同。**彻底不可用** |
| 比色·6屏共享固定网格 | 类内最差 0.67 / 类间最好 0.67 | 采样点大半落在共享深色底 |
| 比色·按跨屏方差选点 | 类内最差 **0.08** | 方差最大的点是**文字抗锯齿边缘**，4px 偏移即变色 |
| cv2 模板匹配 @1/4 降采样 | 裕度仅 +0.110 | 降采样抹细节，不同按钮形状趋同 |
| OCR 无置信度阈值 | `背包`→`背包電`，置信 0.722 | 必须设阈值 |
| 纯 numpy 手写模板匹配 | **1100ms/次** | 必须用 cv2（24ms） |

### 可用（最终选型）
- **A. 多点比色 ~2ms** —— 两个硬条件：
  ①采样点须落在纯色块**深处**：用 **11x11 窗口**内跨屏最大标准差 **<1.0** 筛选
  （3x3 约束→类内 0.17 ❌；11x11→类内 **1.00** ✅）
  ②每通道容差：**待用真机数据重标**。原写的 **35 是错的**——它是拿合成扰动
  （`bright ×1.10`）标出来的，而**实测屏幕亮度对截图像素毫无影响**（见文末「亮度实验」），
  那个扰动根本不真实。参照系：大漠 `CmpColor` 相似度 **0.9 ≈ 每通道容差 25**。
- **B. cv2 `matchTemplate(TM_CCOEFF_NORMED)`** —— 全屏 1600x720 搜 120x60 模板：
  **1/1 = 24ms，类内最差 0.934 / 类间最好 0.498（裕度 +0.436）**，阈值 **0.70~0.85**。
  **唯一能同时输出按钮坐标的方案 → 点击定位必用。**
- **C. OCR ROI** —— 必须 `use_det=False, use_cls=False, use_rec=True`：**1001ms → 9ms**。
  返回 `[['日常任务', 0.993]]`，取 **`res[0][0]`**（`r[1]` 是置信度不是文本）。
  **置信度阈值 ≥0.9**（`日常任务`0.993✅/`倩女幽魂`0.999✅/`背包`→`背包電`0.722❌）。

### 级联
```
① 比色(2ms) → 命中即返回界面ID
② cv2模板匹配(24ms) → 峰值≥0.8 → 界面ID + 按钮坐标
③ OCR ROI(9ms) → 置信≥0.9 → 语义确认
④ 全不中 → 存截图 + 停手报警（LLM 兜底默认关）
```
建图阶段用 LLM 视觉（花 token 一次），运行阶段**永不调 LLM**。

### ⚠️ 级联里被打脸的两次（务必照抄结论，别重走）

**1. 比色不能做决策层，只能做【候选筛选】。**
容差 35 是为抗亮度漂移（界面亮度 +10% 时必需），但它同时让**配色相近的界面互相混淆**：
实测一个**未登记**的灰色系"设置"界面被误判成"背包"（比色 1.00 vs 次高 0.00，领先幅度
大到 margin 判据也拦不住）。比色是"相似度"不是"语义"。
→ **正确级联：比色选候选（≤3 个）→ 模板匹配确认 → 才接受**；候选为空则全屏模板匹配。
改后同一张未登记界面被**正确拒绝**（`screen=None`）。

**2. 锚点必须带搜索区(roi)，否则性能崩。**
不给 roi 就全屏搜 1600x720：**80ms/次**；自动外扩 120px：58ms；外扩 **48px：数 ms**
（匹配成本 ∝ roi 面积 × 模板面积）。建图时自动给锚点设 `roi = box ± 48px` 即可。

### PC 端建图工具链实测（`E:/AiDemos/QnyhAuto/mapkit/`，合成界面自检）
```
① 建图自检    类内最差 1.000  vs  类间最好 0.000   ✅ 比色可分离
② 级联识别    30/30 = 100%   (全部 color+template 命中)
③ 关掉比色层  模板匹配 6/6 = 100% 接住，峰值 0.980~0.989
④ 未登记界面  正确拒绝 (screen=None) —— 无误判

```

## 二、注入通道暴露面

| 通道 | 事件层证据 | 检测点 | 隐蔽性 |
|---|---|---|---|
| PC adb `input` | `deviceId=0`、`source=0`(非 SOURCE_TOUCHSCREEN)、`pressure=1.0` 固定、`size=0`、无历史采样点 | ①`getDeviceId()` ②`getSource()` ③`Settings.Global.ADB_ENABLED` ④无对应 InputDevice | 最低 |
| 手机端无障碍 `dispatchGesture` | `source` 正常但 **`deviceId=-1`** | ①`AccessibilityManager.getEnabledAccessibilityServiceList()` **直接抓包名** ②框架包名黑名单(`com.cyjh.mobileanjian`/`org.autojs`/`com.touchsprite`) | 中 |
| root + uinput | 注册成真实输入设备，带正常 deviceId/pressure/size | ①`InputDevice.getDeviceIds()` 可疑名 ②`/proc/bus/input/devices` ③root/Magisk 检测 | 高 |
| 硬件 HID(OTG 模拟触摸屏) | 系统视为真外接设备，游戏无法区分 | 只剩行为分析 | 最高 |

### 独立于通道的检测面
1. **已安装应用扫描**（遍历包名找按键精灵/触动/AutoX/GG）→ **自制脚本优于知名框架的核心理由**
2. **VMOS/云手机痕迹**（用户机装了 `com.vmos.pro`）
3. **`FLAG_SECURE` 截屏拦截** → adb `screencap` 得全黑图（硬限制，上机先验）
4. **行为风控（网易易盾，权重最大）**：点击分布、轨迹曲率、反应时延、在线时段、操作序列重复度

### 关键判断
**行为风控权重 > 注入通道检测。** 优先级：行为拟人（已实现）> 通道隐蔽 > 框架选择。
通道再好，恒定节奏+固定坐标+24h 在线一样被盯上。

## 三、用户机（华为 WLZ-AL10 / HarmonyOS 4.2）硬约束

- **没有原生「无线调试」开关**（华为官方支持页确认，适用版本含 HarmonyOS 4.2）。
  无线 adb 必须**先 USB 连一次** → `adb tcpip 5555` → `adb connect <IP>:5555`。
- **华为自 2018 年停止 bootloader 解锁 → 基本不能 root**：
  uinput 真触摸注入 / Magisk 方案不可用 → 手机端注入只能走**无障碍 `dispatchGesture`**。
- USB 连接方式会自动回落「仅充电」→ 设备从 `device` 掉成 **`offline`**（非 unauthorized）。
  需重插/换线/换口；`adb reconnect` 救不回物理链路问题。
- 本机 DLP 禁 C++ → 手机端**不能**集成需要 NDK 的 OCR（PaddleOCR-ncnn、tess-two）。
  → **手机端运行时只用比色 + 模板匹配（OpenCV Android aar 有预编译 .so，无需 NDK）；
  OCR 只在 PC 建图阶段用一次。**

## 四、亮度实验：屏幕亮度【不影响】截图像素（2026-09-18 真机实测）

**结论：屏幕亮度（背光）与截图/比色的像素值无关。** `screencap` 抓的是 SurfaceFlinger 合成后的
**帧缓冲内容**（GPU 渲染出的 RGB 数字值）；亮度施加在**显示面板/背光层**，位于帧缓冲之后，
是物理层面的事。大漠 `GetColor`/`CmpColor` 读 PC 窗口渲染数据，显示器背光同样不影响。

真机实测（HUAWEI WLZ-AL10，倩女幽魂前台，`scripts/test_brightness.py`）：
```
亮度 37(原始) vs 5(最暗)     平均差 0.106  最大差 17  变化>10 的像素 0.0004%  96.11% 完全相同
亮度 37(原始) vs 255(最亮)   平均差 0.093  最大差 17  变化>10 的像素 0.0005%  96.44% 完全相同
亮度 5(最暗)  vs 255(最亮)   平均差 0.104  最大差 17  变化>10 的像素 0.0006%  96.17% 完全相同
```
**判定依据**：亮度差 32 级（37→5）与亮度差 250 级（5→255）造成的差异**几乎相同**
（0.0004% vs 0.0006%）。若亮度有影响，后者应显著更大 → 那 0.0006% 来自两次截图间隔
（2.5s）里**游戏画面自身在动**，与亮度无关。12 个采样点在**容差 0（逐位全同）下仍 12/12 命中**。

**改设置的方法**（可逆）：`settings put system screen_brightness_mode 0` +
`settings put system screen_brightness <0-255>`；**事后必须还原** `mode`（设回 1 = 自动；
自动模式下数值由系统接管，读回值会漂移，属正常）。

### 真正的扰动源（容差解决不了，要靠【选点避开】）

| 扰动源 | 影响截图像素 | 处理 |
|---|---|---|
| 屏幕亮度 / 自动亮度 | ❌ **不影响**（已实测） | 无需处理 |
| 护眼模式 / 色温（厂商实现不一） | ⚠️ 可能（部分实现改在合成层，会被截到） | 需实机验 |
| **弹窗弹出的全局变暗遮罩** | ✅ **影响大，且会压暗 HUD** | 采样点避开会被压暗的区域；或按「有/无弹窗」分状态取点 |
| **半透明 UI 透出场景** | ✅ **影响大** | 选点落在**不透明** UI 元素上 |
| 场景光照 / 昼夜 / 天气 | ⚠️ **只影响半透明 UI / 透出场景的区域；不透明 UI 面板不受影响** | 采样点落在不透明 UI 元素上；避开 HUD 半透明底、聊天框底 |
| **UI 开合动画进行中** | ✅ 影响 | 时序问题：**等动画结束再截图**（操作闭环已要求动作后截图核对） |
| 游戏内画质档位 | ✅ 影响 | 固定档位后重标 |

### 因此更好的选点算法（取代"合成扰动"法）

**跨状态重复采样选点**：同一界面在**多种真实状态**下各截 N 张
（有/无弹窗、不同地图光照、不同时段），对每个像素计算 [跨状态方差小] × [跨界面差异大]，
取乘积最大且满足平坦约束的点。这样选出的点**天然免疫**上表里的真实扰动，
而不是靠放宽容差兜住——放宽容差会让"配色相近的界面互相混淆"（见前文比色误判）。

## 五、容差到底怎么定（三份实测合起来才完整）

1. **屏幕亮度不影响截图像素**（§四，实测）。
2. **真机静态像素的帧间噪声 ≈ 0**：两次截图（间隔 2.5s）有 **96.11% 的像素逐位完全相同**，
   仅 0.0006% 变化且来自**画面动画**（§四同一实验）→ 类内漂移的真实来源只有「位移」。
3. 我合成基准里用的 `noise σ6` 是**悲观假设**，它把类内漂移抬到 ~17~23；
   **真机上容差 5~10 就够**。

**定容差的正确顺序**（不要再用合成扰动猜）：
① 建图时对同一界面**多次截图**，**实测**该屏的类内漂移 →
② 容差取「实测类内漂移 + 余量」→ ③ 校验「相邻界面色调间距 > 容差」，不满足就换点或加候选色。

**定量规律（合成扫描实测，`mapkit/selftest_neartone.py`）**：
```
容差下限 = 类内漂移          容差上限 = 相邻界面色调间距 − 1
判别窗口存在 ⟺ 色调间距 > 类内漂移
合成 σ6 假设下：间距需 > 约 25~30（s=20 时窗口刚好消失，s=30 起窗口宽 14 档）
真机噪声≈0 时：间距需 > 约 5~10 即可
```
→ 结论：**多点签名确实能区分色调接近的界面/场景**，但判别力 = 点的空间分布 × 容差宽度，
两者耦合；**容差不是越小或越大越好，要落在「类内漂移」与「相邻间距」之间**。

### 多点签名 vs 同点多候选色（别混为一谈）
| 机制 | 结构 | 判别力来源 | 何时有意义 |
|---|---|---|---|
| **多点签名** | **多个不同坐标**各一个色 | **空间组合**（色差无需大） | 始终——这是主力 |
| **同点多候选色** | **同一坐标**多个色 | 只在候选色彼此差 > 容差时有意义 | 该位置在不同状态下颜色**大幅**变化（遮罩压暗/高亮）时 |
例：`考状元不Color` 7 点是 7 个不同坐标（多点签名）；`hud_S1~S7` 是同一坐标 (1089,118)
的 7 个色，彼此最大差 14 < 大漠 sim0.9 的 25 → **那一处属冗余**。
