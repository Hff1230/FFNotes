# 半自动采集手机界面

**一句话**：用户只管在真机上走界面，agent 在后台盯着；一遇到「识别器不认识」的界面就**自动**弹取点工具，
用户鼠标点几下 → 自动校验 → 入库 → 继续盯。**加界面不改代码，也不需要人喊「开始」。**

这是**人机分工协议**：机器做「监控／校验／入库／回归」这类确定性工作，
人做「这是哪个界面、这个按钮在哪」这类只有人知道的事。

> 姊妹技能 `vision-annotation-toolchain` 讲**工具链原理**（放大镜为什么必须 NEAREST、点质量怎么分级）；
> 本技能讲**怎么跑完一整轮**：从 adb 连上，到新界面进图谱、回归变绿。

## When to Use / 何时用

- 要给「截图 → 比色／模板／OCR 判别」管线补新界面、新按钮
- 界面是**动态的**（游戏 HUD、含动画），纯算法自动建图不可靠
- 按钮**紧邻付费／删除／退出等危险入口**，不敢盲点、必须人确认
- 用户已表示愿意「人工把界面走一遍」

不适用：纯离线静态截图集（直接跑项目自己的批量建图脚本）；不需要人介入的纯算法选点。

## 角色分工（别搞反）

| 角色 | 谁 | 做什么 |
|---|---|---|
| 人 | 用户 | 在手机上切到目标界面并**停手**；在取点图上点选；点完按 ESC |
| 人 | 用户 | 决定「这个界面叫什么」——工具顶部输入框填 |
| 机 | agent | 守护、识别、判断认不认识、弹工具、校验、入库、回归、报数 |
| 机 | agent | **绝不**代替人给未识别界面猜名字（会污染图谱） |

**铁律**：识别器**不认识就返回 `None`**，不许「返回最像的那个」。宁可停下弹工具。

## 端到端流程

### 0. 开工：由 agent 一键拉起（**每次都手动起，不装开机自启**）

**规矩（用户明确要求）**：用户说「开始采集」→ agent **主动**把下面几样起起来，**不要问、不要装
开机自启**。gateway 用手动模式，重启即失效，所以每次开工都要重起 —— 这就是「每次开启采集时直接启动」。

```bash
cd <工程根>

# (1) 设备在线（必须有 1 台 [device]，否则先解决连接）
python "<skills>/tools/adb-device-control/scripts/adbctl.py" devices

# (2) 守护：不认识就自动弹取点窗（后台常驻）
<VenvPython> scripts/auto_annotate.py --interval 1.6 --stable 2

# (3) 屏幕悬浮字：实时显示当前界面（**首选反馈通道**，见下节）
<VenvPython> scripts/hud_overlay.py --pos 20,20     # 左键拖动挪位，右键关闭

# (4) 兜底：用户发字时即时报当前界面（~1.5s 出结果）
<VenvPython> scripts/watch_report.py --force
```

起完先跑 `regress.py` 确认回归 100%，再让用户开始切界面。

- `--stable 2`：连续 2 帧识别一致才弹 → 躲开切界面动画／过渡态
- 后台进程**接 notify 或定期 poll**（用户对静默零容忍，见「回报纪律」）
- **悬浮字是首选反馈通道**（秒级、零 token、不占对话框）；cron 播报已 pause，**别擅自 resume**
- 状态文件要**去重**：只在 `sid` 变化时更新／输出，否则刷屏

### 1. 用户操作手机（说完这句就别再管）

> 「你把手机上要采集的界面一个个走一遍，**停住**就行。遇到我不认识的我会自动弹窗口：
> **空白颜色块上点一下 = 比色特征点**；**要记成按钮的就点完在弹框里填名字**。
> 顶部『界面名』框帮我填这个界面叫啥。点完按 **ESC**。不用叫我。」

### 2. 取点（工具自动弹）

取点 GUI 的交互契约：

| 操作 | 效果 |
|---|---|
| 左键点 **空白颜色块** | 记为**比色特征点**（弹框**留空**） |
| 左键点 **按钮／图标** | 记为**动作坐标**（弹框**填名字**，如 `打开背包`） |
| 顶部「界面名」输入框 | 决定写进图谱的 screen id，**以它为准** |
| 方向键 / `R` / `E` / `ESC` | 微调 1px / 重载图 / 清空 / **提交并退出** |

**取点规则（用户拍板的核心契约）**：

- **仅空白点作为比色特征点使用，有备注的点作为按钮使用**
- 特征点必须落在**纯色区**（状态栏实时 `std` ≤ 6），别点图标／文字中心
- **按钮中心不是合格特征点**（std 常 36~86），但它仍是有用的动作坐标 → 填名字即可

### 3. 入库（ESC 后自动，也可手动）

```bash
<VenvPython> scripts/merge_picks.py evidence/annot/<图>.picks.json --apply
```

- 带 name → `clicks[name] = [x,y]`
- 不带 name → 全局比色点（查 `std` + 与其它标签**撞色**）
- **必须真剔除**坏点（`bad_xy`），不能只打印 ✗
- 写盘前自动备份到 `Tools/backup/<时间戳>/`

⚠️ **手动起的取点工具不会自动入库**：`auto_annotate.py` 只在**它自己弹的**窗口 ESC 后才调
`merge_picks --apply`。agent 手动 `pick_point.py` 起的那个，用户按完 ESC **东西还没进图谱** ——
必须自己再跑一次入库，否则用户会回来说「我采了怎么还不认识」。

### 4. 回归（唯一能立刻暴露污染的检查）

```bash
<VenvPython> scripts/regress.py
```

判据：**准确率 100%，平均 ~20ms**。掉一点都要查——标注数据的污染往往是静默的。
**但注意：回归全绿 ≠ 新界面能被识别**（见坑 10）。

## 实时状态反馈：飘在屏幕上，别纠缠投递通道

用户要在操作过程中「知道现在是什么界面」，而且他**操作很快**。**不要把时间花在
「怎么把消息送进对话框」上** —— 本地桌面会话**没有**秒级的消息投递通道：

| 想法 | 实测结果 |
|---|---|
| cron 提速 | ❌ 最小粒度 1 分钟（`'20s'` 直接被拒），跟不上人工切界面的节奏 |
| `hermes send` | ❌ 只能投递**已配置的消息平台**（Telegram／Discord…），桌面会话不在目标里 |
| `webhook --deliver-only` | ❌ 零 token 直投，但同样要求 `--deliver` 是真实平台目标 |

✅ **正解：把状态直接渲染到屏幕上**，完全不碰消息通道：

1. 守护每次识别（成功／未知）写 `evidence/annot/_overlay.json`
   （含 `name` / `sid` / `known` / `conf` / `ts`）
2. `scripts/hud_overlay.py` 开一个 **无边框 + 置顶 + 半透明** 的 tkinter 小窗，每 0.3s 读该文件
3. 认识的 → 绿字「界面名 + 置信度 + 时间」；不认识 → 红字（同时守护仍会弹取点窗）
4. 左键拖动挪位、右键关闭、`--pos x,y` 指定位置

延迟 ~1.6s、**零 token**、用户不用切窗口。这是用户拍板的方案（原话「**可以直接在屏幕中飘字**」）。

### 悬浮窗上的「动作按钮」：让 agent 有能力代劳关界面

用户会要求把**动作**也做到浮窗上（原话「**在提示框附近添加个关闭按钮，关闭当前界面**」）。
形状：标题行显示当前界面，下面一行放按钮 + 提示。

```
┌─────────────────────────────────┐
│ 手机界面：福利首页   0.967  17:55│
│ [✕ 关闭界面]  左键拖 / 右键关窗  │
└─────────────────────────────────┘
```

**点下去就是真点手机**，所以护栏必须写在按钮回调里（四条，缺一不可）：

1. **当前界面不认识（`known=false`）→ 不动作**，只提示「不敢乱点」
2. **该界面没定义 `closer` → 不动作**（主界面 HUD／加载页／选服就是这种，属正常）
3. **`closer` 坐标与该界面 `danger` 重合 → 拒绝执行并报警**（双重保险；数据错了也点不出去）
4. **只点 `closer` 里逐个列出的坐标**，绝不临场推断；多步路径（如签到页
   `[(1332,121),(1350,56)]`）按顺序点、每步之间 sleep ~1.3s

执行期间按钮上要显示进度（`正在关闭 福利首页 …(1/2) (1332,121)`），完成后变色提示
「已关闭：xxx」，随后守护会在 ~1.6s 内识别到新界面、浮窗自动更新。

> 控件写法、状态文件协议、`norm_closer()` / `danger_xy()` 规整函数、坐标验证闭环见
> **`references/overlay-widget-recipe.md`**。

**⚠️ 这个按钮的可用性严格依赖坑 3f**：`closer` 格式不统一时按钮会**静默崩溃**，用户只看到
「点了没反应」，完全不知道是代码炸了。**做按钮前先做 3f 的规整。**

## 别踩这些坑

1. **`x or y` 的 falsy 陷阱会打崩管线**：空列表是 falsy，`spec or color_sig` 会静默落到后者；
   新标签签名若是 `[[]]` → `spec[0][2]` 直接 IndexError 把识别打崩。
   → 新增标签签名**补齐到 `len(points)` 个槽位**（哪怕全是 `[]`），取用处加
   `if not spec or len(spec[0]) < 3` 防护。
2. **加了约束常量 ≠ 接进了逻辑**：`MAX_DRIFT` 定义齐全、注释完整，但判断处**没引用** → 误判照旧。
   加完必须**正样本 + 负样本各跑一次**确认真会拦，且**回归没被带坏**。
3. **校验只打印 ✗ 不剔除 = 没校验**：实测点集 16→21 → 签名长度不齐 → `(21,3) vs (0,)` 广播失败 → 识别器崩。
3b. **半截 patch 比不 patch 更糟（本流程最大的坑）** —— 一次改动常牵连三处：
   **(a) 变量定义 (b) 新分支的写入 (c) 坏点的剔除**。只改一处 → 运行时报 `NameError` 崩掉，
   或者**静默不落盘**（用户以为入库了，其实白点，回头来问「为什么不认识」）。
   实测一次踩全：`bad_xy.add()` 写了却没 `bad_xy = set()`（崩）；带名字的点 `continue` 跳过
   却没写 `clicks`（按钮**永远**入不了库）；`point` 分支不建新界面（新界面连壳都没）；
   坏点只收集不剔除。
   → 改完**立刻拿真实 picks.json 跑一次 `--apply`**，比对写盘前后 `clicks` / `points` 的数字，
   确认真的落盘。**别只看代码「看起来对」**。

3c. **用户说「我已经入库了」但识别器仍不认识 → 先查入库脚本有没有崩，不要先怀疑用户操作。**
   实测：用户按 ESC 完全正确，是 `merge_picks.py` 崩在 `NameError` → 点全丢。
   判据顺序：① 跑一次回归看识别是否真的能命中；② 看 `Tools/backup/` 有没有**新**备份目录
   （没新备份 = 没写盘）；③ 直接读 `screens.json` 里的 `clicks` / `points` 数字对不对。

3d. **空白/占位界面名会造出「永远认不出」的垃圾界面 → 守护无限弹窗** ——
   实测：守护弹工具时预填 `--screen unknown`，用户没改 → 图谱里出现 `unknown`
   （无名字、无 `keys`、点又全 ★）→ 识别器永远返回 None → 一直弹，用户会问
   「**刚刚采集的界面怎么又弹出来了**」。
   **两头都要堵**：① 守护**不要**传 `--screen unknown`（传空）；
   ② 取点工具写盘时若名为空或等于 `unknown` → **弹框强制命名，不填就不写盘**。
   配套：顶部输入框**空着/还是占位名时标黄**，标签写成红色「【必填】」—— 否则用户会以为
   「识别器已经给了名字、不用管」。

3e. **有的界面根本没有纯色区**（纯图标／渐变／活动页）→ 人怎么点都是 ★ → 全被剔除 → 零特征。
   这类界面**只能靠 OCR 关键词**。补法：拿它的截图跑一遍本地 OCR（`RapidOCR`），挑 2~3 条
   **该界面独有**的文字当 `keys[].roi`（实测：月卡页用 `特权月卡` / `超值月卡` / `购买立得`
   → conf 0.96~0.99 稳定命中）。**别硬找纯色点**。

3f. **`closer` / `danger` 的两套格式会静默废掉「关闭界面」和安全护栏** ——
   实测用户报「点了关闭按钮没反应」的真因**不是坐标错**，而是：图谱里 `closer` 混用
   `[1364,48]`（一维）与 `[[1350,56]]`（二维）两种写法，而点击代码写 `for x, y in closer`
   → 一维那种遍历出**单个 int** 去解包 → `TypeError: 'int' object is not iterable`，
   **一个点击都发不出去**（用户只看到「关不掉」，完全看不出是崩了）。
   `danger` 同样混用 `{'screen':..,'xy':[x,y],'why':..}`（字典）与 `[[447,420]]`（坐标），
   按 `tuple(p)` 取会得到**键名元组** `('screen','name','xy','why')` → **禁区检查静默失效**。
   → 读取端**必须规整**（`norm_closer()` / `danger_xy()`，见 references），并把数据统一回写为二维；
   排查「按钮没反应」类问题，**第一件事是看进程日志里的 traceback** —— 那是最快的铁证。
   顺带：写数据时也要统一，别让两种格式再回流。

4. **以人工点为准确**：OCR 文字中心与用户点的图标中心**实测 y 差 42px**（图标在文字上方）。
   不要「用 OCR 覆盖人工」。
5. **用户的命名可能基于误解**：用户可能把某高亮图标指认为「关闭」，实测点它**进付费页**。
   → **按他的意图理解（「关掉当前界面」），按实测事实纠正坐标**，绝不把危险坐标存成 `closer`；
   并把已验证的那条绕路写进数据。

5b. **但别急着把用户的说法判定为「记错了」/「误解」——先核对原始数据。** 实测反转：
   用户说「我确定填了福利首页」，我先认定他记错 —— 读 `*.picks.json` 才发现**他 17:27 那次
   确实填了并完整落盘**，是我在**另一次**（守护预填 `unknown`）上丢的名字。
   **判据：直接读每个 `*.picks.json` 的 `screen` 字段 + `picks[].name`**，一眼看出用户填了哪个框，
   别靠推断、别下结论说用户没填。

5c. **界面名一律以用户的叫法为准。** 用户把月卡充值页叫「**福利首页**」，那就叫福利首页。
   助手起的名字（「月卡充值页」）哪怕更准确，也会让用户在对话里对不上号、以为你没听见他说话。
   `name` 只是显示名、`sid`（英文 id）不变，改名不影响识别，**放心按用户口径改**。
   推论：**给界面起的名字要先问用户怎么叫**，别自己拍板。实测还踩过「包裹 vs 背包」同一坑。
6. **判「✕」用亮像素占比**，别用形状／字符画：线状 ✕ **16~25%**，实心图标 **>60%**。
   低分辨率下「实心斜纹」与「✕ 两条对角线」几乎同形（曾据此误判点进充值页）。
7. **动态场景别用全屏像素比判「是不是同一界面」**：角色／背景一直在动 → 同一界面被测成 74% 不同屏。
   要用**固定 UI 区**（标题栏／按钮排）+ 文字判定。
8. **最高分落在已知危险入口时，直接判死这个界面没有该图标**，别换模板反复试——只会反复命中它。
   宁可停下来问用户。

9. **截图失败时「旧图」会被当成新画面（最阴的一个）** —— 截图固定写到同一个文件
   （`_live.png` / `_report_live.png`），adb 偶发产出坏 PNG（`libpng bad header`、
   `imdecode` 返回 None）。**若只校验文件大小，上一次的旧图还在原地、解码照样成功**
   → 于是把「用户已经离开的那个界面」当成当前界面报出去。
   症状：用户说「**我换了界面，你没反应啊**」，而你报的还是上一屏（日志里 `A → B → A` 乱跳）。
   → 截图函数三件套：**① 先 `os.remove(path)` ② 真解码一次校验（不是只看 size）
   ③ 失败重试 3~4 次**。另外**守护与任何旁路轮询（播报器／cron）会同时抢 adb**，
   坏图概率大增 → 两边必须共用这个健壮函数。

10. **回归全绿 ≠ 新界面能被识别** —— `regress.py` 只跑「建图样本」里那批图。给新界面补完
    `keys` 后再跑仍是 37/37，**因为回归样本里根本没有这个界面**。
    → 补完 keys／特征点，必须**拿这个界面自己的截图单独 `identify()` 一次**，看它真返回该 sid
    （实测：补完月卡页 keys 后 regress 无变化，单独跑 `01_unknown_*.png → welfare_monthcard
    conf=0.961` 才是真凭据）。

11. **验证按钮坐标用「真点一次 + 立刻重新识别」闭环，别猜也别只看截图** ——
    确认某坐标是不是真关闭键，唯一可信的办法是走一遍闭环：
    **① 先做危险检查**（`closer ∩ danger` 非空就拒绝）→ **② 记录当前界面**（基线）→
    **③ `human_input.py tap x y` 真点一次** → **④ sleep ~2.5s 后重新识别，变成预期界面 = 有效**。
    实测：点 `(1346,61)` 前「背包 panel_bag」→ 点后「主界面 HUD conf=0.989」= ✅。
    反面教材：`(1345,63)` 这个「看起来对」的坐标来自**建图脚本里硬编码的 `CLOSERS` 表**，
    扫描该区域发现亮像素占比只有 7.8%（远低于线状 ✕ 的 16~25%）→ 那片区域**根本没有 ✕**。
    → 结论：**建图脚本自动生成的 `closer` 一律视为未验证**，必须人点或闭环实测过才能用。

## 回报纪律（用户明确要求）

- **不要问「可以开始下一步了吗」**——守护自动推进，用户的动作本身就是触发信号
- 长耗时（全量 OCR／回归）**主动报进度**：在等什么、等了多久、下一步
- 报结论要**数字**（准确率 N/N、ms、点数），不要形容词
- 阻塞在用户身上时**立刻说明**（如「请把手机停在目标界面」）
- **状态类反馈的通道优先级**：屏幕悬浮字（实时）> 用户发字即查（兜底）> 对话周期性播报（已被否）
- **不要跟用户争论他记没记错** —— 去读原始数据（坑 5b）
- **用户报症状（「关不掉」「你没反应」「还是识别错了」）时，先去找等价的技术真因**
  （崩溃 traceback／数据格式／旧图残留），别先当成需求变更或用户操作问题
