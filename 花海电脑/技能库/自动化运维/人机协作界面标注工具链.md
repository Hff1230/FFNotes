# vision-annotation-toolchain

当截图驱动的识别管线遇到「没见过的界面」时，靠算法猜是错的 —— **让人类点一下最快**。

本技能是**人机协作建图的完整链路**：`取点 GUI → 点质量分级 → 冲突校验入库 → 守护自动发现`。

**适用**：手游/App 界面图谱补建、OCR 模板标定、任何「截图 → 图色/模板判别」管线的标注工作。
**不适用**：纯算法自动建图（那走项目自己的建图脚本）；也不需要本技能时不要硬套。

> 姊妹技能 `mobile-game-automation` 讲**怎么用**图谱驱动游戏；本技能讲**怎么把图谱建出来/补全**。

## 何时用

- 识别器返回「不认识」（`None`）→ 需要为新界面补特征点
- 需要人类指认按钮坐标（算法量不准，或按钮紧邻付费/危险入口不敢盲点）
- 已有图谱要扩充或校正（**人工点通常比自动选点更准** —— 人知道哪个元素是这个界面独有的）

## 四条不可省的规则

### 1. 取点 GUI 必须有「像素放大镜」

凭缩略图/文字描述量坐标会**系统偏移**（实测 y 误差可达 50px）。放大镜必须满足：

- **NEAREST 放大**（**不要 LANCZOS** —— 插值会糊掉像素边界，就没法判断"这是不是纯色"）
- **十字准星标出当前像素 + 绿框标出该像素边界**
- **跟随鼠标 + 靠近窗口边缘自动翻到另一侧**（不遮挡待点位置）
- **状态栏实时显示：单点 RGB / k×k 中位数 / std / 评级**
- 参考参数：20×20 原图像素 → 8× → 160×160 显示

### 2. 点质量必须量化分级，别靠肉眼

对候选点取 **k×k（k=11）邻域色值中位数 + 最大通道 std**：

| std | 评级 | 含义 |
|---|---|---|
| ≤ 2.5 | ★★★ | 纯色区，首选 |
| ≤ 6 | ★★ | 勉强可用 |
| > 6 | ★ | **不可用** —— 落在文字/图标/边缘上，抗锯齿会变色 |

**关键认知：按钮"中心"通常不是合格的特征点。** 按钮中心是图标/文字，std 必然大（实测 36~86）。
要选**按钮的底色空白处**、**面板的大片背景色**、**未选中页签的底色**。

### 3. 两类点必须分流（用户可混着点，靠"有没有备注"自动判）

| 点法 | 用途 | 校验 |
|---|---|---|
| **留空备注** | 比色特征点 → 进点集 | 必须 **std ≤ 6**；且与其它标签在同位置**不撞色**（色差 ≤ tol 即剔除） |
| **有备注** | 动作坐标 → `clicks[名字]` | 只要位置准，**std 不查**（按钮中心本来就在图标/文字上） |

用户在命名弹框里留空或填名字即可，不需要额外切模式。

### 4. 入库校验必须「真拦截」

**只打印 ✗ 不算校验。** 实测踩坑：校验代码打印了 ✗ 但**仍继续写盘** → 点集 16→21、
各标签签名长度不齐 → 数值广播失败 `(21,3) vs (0,)` → **整个识别器崩掉**。

必须做到：

- 收集 `bad_xy` 集合并**从入库集合里剔除**
- 写盘前**断言「所有标签的签名长度 == len(points)」**
- 改完标注数据**跑一次全量回归** —— 这是唯一能立刻暴露这类污染的手段
- 写盘前自动备份（时间戳目录），便于回滚

## 全局点集的补采约束（最容易漏）

若管线用**全局点集**（一份坐标 + 每个标签各自的色值签名），那么人工只为**一个**标签取点时：

> **必须从其它标签的建图样本，在新点坐标上补采色值**，否则签名长度不齐，**整套比色立刻失效**。

补采时每个标签取若干张样本、每张取一个中位数色 → 形成**多候选签名**（抗状态变化）。

## 未识别界面守护（让用户不用喊）

**不要每轮问用户「可以开始下一步了吗」。** 写一个守护进程：

```
循环（每 1.5~2s）:
  截图 → 识别
  若识别成功 → 记录状态，继续
  若识别失败（None）:
      连续 stable 帧（默认 2）结果一致才触发      ← 躲开切换动画/过渡态
      截图指纹去重：同一画面只弹一次              ← 避免反复打扰
      弹取点 GUI（阻塞，用户点完 ESC）
      自动 校验+入库 → 继续监听
```

- **指纹**：缩到 32×14 灰度后 hash（对轻微噪声不敏感，能识别"还是这屏"）
- **STOP 文件**作为停止开关（比 Ctrl+C 更适合后台进程）
- 取点 GUI 顶部必须有**标签名输入框**（写盘以此为准）—— 守护进程无法可靠自动命名未知界面，
  让用户核对/修改，**不要用识别器的建议值覆盖用户的输入**

## 常见坑

1. **全屏像素比对判「是不是同一界面」只适合静态面板。** 动态场景（游戏主界面、视频、动画页）
   角色/背景一直在动 → 实测**同一界面被判 74% 不同屏**。动态场景要用**固定 UI 区**
   （标题栏/按钮排）+ 文字判定，不要全屏比。
2. **区分「线状图标」与「实心图标」要用亮像素占比**，形状/字符画不够：
   低分辨率字符画下「实心斜纹图标」与「✕ 两条对角线」**几乎同形**（我据此误判并点进了充值页）。
   量化判据：区域灰度阈值化后的**亮像素占比** —— 线状 ✕ 约 **16~25%**，实心图标 **>60%**。
3. **人工标定点优于 OCR 文字中心**：实测同一按钮，OCR 文字中心与用户点的图标中心 **y 差 42px**
   （图标在文字上方）。**以人工实测点为准**，不要"用 OCR 覆盖人工"。
4. **加了约束常量 ≠ 接进了逻辑**：`MAX_DRIFT` 定义好、注释齐全，但判断处**没引用它** → 误判照旧。
   加完约束必须**用正样本 + 负样本各跑一次**确认它真的会拦，**并确认没把正常识别带坏**
   （加严校验容易误伤，回归必须过）。
5. **`x or y` 的 falsy 陷阱会打崩管线**：空列表是 falsy，`spec or color_sig` 会**静默落到后者**；
   新增标签若签名是 `[[]]`，`spec[0][2]` 直接 `IndexError`。→ 新增标签的签名**必须补齐到
   `len(points)` 个槽位**（哪怕全是 `[]`），并在取用处加 `if not spec or len(spec[0]) < 3` 防护。
6. **别把「最像某图标的位置」当答案**：若匹配最高分落在**已知危险入口**（付费/删除/退出）上，
   **直接判死该界面没有这个图标**，别换模板反复试 —— 只会反复命中它。宁可停下来问用户。
7. **用户的命名可能基于误解，要按意图而非字面执行**：用户可能把某个高亮图标指认为「关闭」，
   而实测点它会进付费页。此时 **按他的意图（"关掉当前界面"）理解，但按实测事实纠正坐标**，
   不要顺着他的命名把危险坐标存成 `closer`。并把"已验证的那条绕路"记进数据。
